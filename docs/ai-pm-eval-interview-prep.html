  1. "We'll add evals later" — they never stabilize
  2. "Our users are our eval" — by the time they complain, damage done
  3. "We have unit tests" — infrastructure tests ≠ quality evals
  4. "We do manual QA" — not repeatable, doesn't scale

Steps vs. Jobs

Step = internal (visible in traces). Job = what the user gets (visible in satisfaction). Litmus test: Can you explain it to a user? Would they file a support ticket if it failed?

Prioritization Formula

Priority = Frequency × Severity × User Impact (each 1-5, multiply — range 1-125). The Cascade Principle: jobs earlier in the chain always have higher severity.

Q2 — ObserveError Analysis & Failure Modes

The Husain-Shankar Methodology (4 Steps)

  1. Open Coding: Review 50 real traces. Freeform notes. NO predefined categories. Let patterns emerge.
  2. Axial Coding: Feed open codes to a frontier LLM. Ask for 5-6 failure categories with percentages. YOU validate, LLM proposes.
  3. Theoretical Saturation: Keep reviewing until no new failure modes. Typically 30-50 traces. Track: new categories per batch of 10 (5→3→1→0 = saturated).
  4. Formalization: Each category gets: clear definition, pass/fail criterion, 2-3 PASS examples, 2-3 FAIL examples.

Q3 — DefineQuality Definition & the ACCT Framework

Quality Formula "User needs X so they can Y without Z." The "without" clause IS the eval north star — it describes the work the AI eliminates. Zero rework = exceptional. Light editing = good. Significant rework = poor. Start over = failure.

The ACCT Framework (4 Dimensions)

DimensionCore QuestionExample Failure
A — AccuracyIs the information correct?"Apple founded 1974" (was 1976)

C — CalibrationDoes it know what it doesn't know?"You definitely have strep"
T — TasteDoes the output feel right?Luxury brand AI writes like intern

Non-Negotiables (Automatic Fail)

  • Trust-breaking: Fabricated facts, hallucinated sources, made-up stats
  • Harm-causing: Offensive content, dangerous advice, privacy violations
  • Contract-breaking: Things product explicitly promises not to do

Required vs. Additional (Hebbia's Two-Tier Approach)

Required = minimum acceptable (SLA). Any failure = output fails. Additional = quality differentiators. Track how many pass. A 60% score means: all Required passed, ~60% of Additional passed. This is NOT a failure.

The 5-Point Quality Scale

ScoreDescription
1Unusable. Fundamentally wrong, harmful, or broken.
2Poor. Some relevant info, but user must start over.
3Acceptable (quality floor). Gets core job done. User edits, doesn't restart.
4Good. Correct, complete, appropriate. Minor polish.
5Exceptional (quality ceiling). Insightful, synthesized, not just correct.

Q3 cont'dDimensions, Rubrics & Test Cases

Discover Eval Dimensions (3 Steps)

  1. Start with error analysis taxonomy
  2. Convert each failure category to a positive dimension: "Stale Information" → "Information Recency"
  3. Validate: Does it map to real failures? Can an engineer fix it? Distinct from other dimensions?

Sweet spot: 3-6 dimensions. Fewer than 3 = too coarse. More than 6 = grading exhaustion + overlap.

Hebbia's 4 Constraints

  • Atomic — single diagnosable issue
  • Binary-Friendly — can make clear pass/fail
  • Specific — "LINE chart for trends, BAR for comparisons" not "appropriate visualization"
  • Distinct — if two dimensions always score the same, they measure the same thing

The Logo Swap Test (for Specificity)

Replace brand name with a competitor's. If output still makes sense, it's too generic. Fails.

Build Rubrics from Scratch

Rubric Standard "A rubric must be so clear that two strangers would agree 80% of the time." Every disagreement is a rubric bug. Fix the rubric, not the graders.

Start binary (PASS/FAIL). Higher inter-rater reliability. LLM judges cluster at 3-4 on scaled rubrics. Forces you to articulate the exact boundary.

3 Components of a Rubric

  1. PASS: Observable, bounded, falsifiable ("contains at least 2 data points" not "demonstrates understanding")
  2. FAIL: At least one concrete failure marker, covers most common failure mode
  3. Edge Cases: Borderline situations with explicit rulings. 80% of disagreements live here.

Cohen's Kappa Validation

Two reviewers independently label 30 traces → measure Kappa → discuss every disagreement → refine until ≥0.6 with new 30 traces.

  • < 0.4: Basically random. Major revision.
  • 0.4-0.6: Moderate. One more round.
  • 0.6-0.8: Good. Target for production.
  • > 0.8: Excellent. Rare.

Anatomy: Input + Context + Expected Properties (NOT exact text)

Sizing: Start 20-30 → 50-75 at 1 month → 100-200 mature. 20 cases detect 0.5+ point diffs. 50 detect 0.3. 100 detect 0.15.

First 20 (2-3 hours): 5 real queries (happy) + 5 real complaints (regression) + 5 edge variants + 3 adversarial + 2 minimum input.

Q4 — DetectAgent-Specific Evaluation

Step-Level Evaluation

An agent is a chain. If link 3 breaks, everything after is garbage. Step-level eval answers: WHERE in the chain did it break?

Eval Gate Design (between steps)

  • After Research: Sources found? Authoritative? Correct entity?
  • After Analysis: Conclusions supported? Specific not generic? (Logo Swap Test)
  • After Generation: Matches analysis? Format correct? Brand-appropriate?
  • After Execution: Actually performed? Parameters correct?
Gate TypeCostSpeedUse When
DeterministicFree<1msCheckable structure
Regex/PatternFree<1msMust contain/exclude patterns
Embedding SimilarityCheap~50msSemantic relatedness
LLM-as-Judge (fast)Moderate1-3sQuality judgment, not complex
LLM-as-Judge (strong)Expensive3-10sNuanced judgment

Tool Use Evaluation (3 Surfaces per Tool Call)

  1. Tool Selection Accuracy — Did it choose the right tool? (Often deterministic)
  2. Argument Correctness — Right tool, correct parameters? (Context-dependent)
  3. Result Interpretation — Right tool, right input, but did agent correctly USE the output? (Hardest — needs LLM judge)

Multi-Turn & Memory (5 Things to Test)

  1. Persistence: Recall planted facts 15+ turns later
  2. Knowledge Updates: When user corrects info, agent uses new version
  3. Abstention: Asked about info never provided → "we haven't discussed that" not inventing
  4. Feedback Incorporation: "Make it edgier" → tone actually shifts, context retained
  5. Context Window Pressure: Test at 25%, 50%, 75%, 90% capacity
Context Rot: Models claim 200K tokens but become unreliable ~130K (~65% of capacity). "Lost in the middle" — high recall early/late, low in middle.

Multi-Agent (4-Layer Architecture)

LayerWhatGrading
1. Individual AgentEach sub-agent's output qualityDedicated test datasets per sub-agent
2. OrchestrationTask decomposition, routing, synthesisDecomp quality (LLM), routing (deterministic)
3. End-to-EndFinal output as user experiences itStandard rubric-based eval
4. EfficiencyTotal tokens, latency, invocationsDeterministic metrics

Build order: Layer 3 first (week 1) → Layer 4 (week 2) → Layer 1 only if Layer 3 below target → Layer 2 if individuals pass but end-to-end fails.

The 60/40 Rule: 60% of checks can be structural (free, instant). Only 40% need LLM-as-judge. Most teams do the opposite.

Structural Checks (First Line of Defense)

Format: Valid JSON, required fields, no [PLACEHOLDER] text, no "As an AI..." preamble
Length: Within range, no suspiciously short responses
Content: Expected sections, valid URLs, reasonable numbers
Safety: No PII (regex), no profanity, no competitor disparagement, no unauthorized advice
Consistency: Brand name consistent, numbers don't contradict

LLM-as-Judge (4-Part Prompt Structure)

  1. Identity statement — "You are an expert evaluator"
  2. Rubric with anchored levels — 1/3/5 with descriptions (prevents score compression)
  3. Forced process — quote evidence → reason → THEN score (chain-of-evidence)
  4. Structured output — JSON for aggregation

6 Reliability Techniques

TechniqueWhen
Chain-of-Evidence (cite → reason → score)Always (non-negotiable)
Anchored Examples (real 1/5, 3/5, 5/5 outputs)When scores cluster at 3-4
Adversarial framing ("find every flaw")When judge is too generous
Reference Comparison (known-good benchmark)When you have golden examples
Multi-Judge (2-3 judges, check agreement)High-stakes decisions
Pairwise A/B (compare two side-by-side)Comparing versions (most reliable)
Self-Enhancement Bias: LLMs rate their own outputs higher. Use a different (stronger) model as judge. Generator = Sonnet? Judge = Opus.

Optimal setup: 100% structural + 10% LLM judge + 1% human review.

Running Evals — Reading Results

  • Mean alone lies. Always report mean, min, max, SD, % below floor.
  • SD < 0.5: Consistent. SD 0.5-1.0: Normal. SD > 1.5: Fix this first.
  • pass@k = at least 1 success in k tries (optimistic). pass^k = ALL succeed (strict).
  • Code generation → pass@k. Customer support → pass^k.
  • Win rate > 60% on 40+ cases usually significant.
Prompt A: Mean 4.0, SD 1.8
Looks great but 20% catastrophic failures
Prompt B: Mean 3.5, SD 0.5
Lower average but zero failures. Better for most products.

Safety & Protection

5 LLM Judge Biases: Self-Enhancement (fix: different model), Position (fix: swap orderings), Verbosity (fix: "brevity preferred"), Sycophancy (fix: "find flaws"), Source (fix: strip metadata).

Eval Contamination: Anthropic's BrowseComp — Claude independently found the benchmark source code and decoded the encrypted answer key. Keep test cases private. Rotate quarterly. Verify reasoning, not just answers.

B2C priority: Safety > Calibration > Taste > Completeness > Accuracy

5 Interview Questions & Great Answers

QuestionGreat Answer Framework
"Design an eval framework for [product]." Start with failure modes → 3-4 specific dimensions → describe test cases → grading method. Red flag: "I'd measure accuracy, helpfulness, and satisfaction."
"How would you know if AI quality is getting worse?" Production quality sampling, implicit signals (regeneration rate), drift detection, automatic alerting.
"5% CSAT drop. Debug it." Segment data → sample 30 low-CSAT outputs → categorize failures → check recent changes → propose fix → contrastive eval before shipping.

The LawThe 10 Commandments

1
Look at your data first. Build evals second.
60-80% of time on error analysis, not infrastructure. — Husain
2
You own the rubric. Engineers own the infrastructure.
Don't delegate "what good looks like." They'll optimize what's measurable, not what matters.
3
Start with 20 test cases, not 200.
Well-chosen cases from real failures beat large synthetic collections. — Anthropic
4
Prefer code checks over LLM judges.
Anthropic hierarchy: code-based > LLM-based > human. Use simplest that works.
5
Run each test case multiple times.
Single run = what CAN happen. Multiple runs = what WILL happen. k≥3 minimum.
6
Never use the same model as generator and judge.
Self-enhancement bias: inflated by 0.3-0.6 points. Miss regressions.
7
Report distributions, not just averages.
Average 4.0 with two catastrophic 1s is worse than consistent 3.5.
8
Check statistical significance before celebrating.
0.3-point improvement on 15 cases might be noise. Use confidence intervals.
9
Add every production failure to your test suite.
Regression cases compound into a quality moat. Never remove them.
10
Calibrate your judge quarterly.
30 outputs, human vs. judge. Kappa < 0.6 = rewrite judge prompt.

ReferenceKey Math & Essential Glossary

Confidence Intervals

SE = SD / √n
95% CI = Mean ± 1.96 × SE
Non-overlapping CIs = real difference
4x cases to halve CI width

Sample Size Guide

Big diffs (0.5+ pts): 15-20 cases
Small diffs (0.2-0.3): 40-50 cases
High variance (SD>1.5): 60+ cases

Win Rate Thresholds

20 cases: 75% needed
30 cases: 67%
40 cases: 63%
100 cases: 60%

Cohen's Kappa

κ = (Po - Pe) / (1 - Pe)
>0.8: Strong. 0.6-0.8: Good (target).
0.4-0.6: Weak. <0.4: Random.
