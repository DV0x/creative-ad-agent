Chapter 15Step-Level Evaluation

First Principle
An agent is a chain. If link 3 breaks, everything after it is garbage — but the final output might look fine because later links compensated. Conversely, the final output might be terrible, but you won't know which link failed unless you check each one. Step-level evaluation answers one question: WHERE in the chain did it break?

The Diagnosis Problem

Imagine a doctor who can only tell you "you're sick" but not where, or why, or what organ is affected. That's what end-to-end eval looks like without step-level evaluation. You know the output is bad. You don't know which step caused it.

This is the most common situation teams find themselves in. The final output scores 2/5 on accuracy. The PM files a bug. The engineer stares at the prompt, changes a few words, runs the eval again, and the score moves to 2.5. Nobody knows if the improvement was luck, if it fixed the root cause, or if it just shifted the failure to a different test case. Three weeks of this and the team is demoralized, the score is still bouncing between 2 and 3, and nobody has actually diagnosed anything.

The fix is not a better prompt. The fix is visibility into each step.

The Error Cascade Math

Here is why step-level evaluation is not optional. It is math.

If your agent has 4 steps and each step has a 90% success rate (which sounds good!), the probability that the entire pipeline succeeds is:

Error Cascade
0.90 × 0.90 × 0.90 × 0.90 = 0.656

A pipeline of 4 steps at 90% each produces a 65.6% end-to-end success rate.
At 6 steps: 53.1%.
At 8 steps: 43.0%.

This is why agents with many steps feel unreliable even when each individual step seems fine. The failures are multiplicative, not additive. A 10% failure rate at each step compounds into a coin-flip at the end. And without step-level evaluation, you cannot tell which step's 10% failure rate is the one worth investing in.

The cascade math also explains why eval gates (which we'll get to shortly) are so powerful. If you add a retry mechanism at each gate and the retry succeeds 80% of the time, a 90% step success rate becomes ~98%. At 4 steps: 0.984 = 0.922. That's a 26 percentage point improvement in end-to-end success rate, achieved not by making any step better but by adding the ability to catch and retry failures between steps.

Why This Matters Practically
Consider an agent that researches a company, writes marketing hooks, generates art direction, and produces images. The final images are bland and generic. Where did it go wrong?
  • Maybe the research step found the wrong company (entity confusion).
  • Maybe the research was fine but the hooks ignored it (context loss between steps).
  • Maybe the hooks were good but the art direction was generic (creative collapse).
  • Maybe everything upstream was great but the image prompt was poorly structured.
Without checking each step independently, you're guessing. With step-level eval, you know in 30 seconds: "Research was correct, hooks were specific, art direction collapsed to generic stock-photo aesthetic. Fix the art direction prompt."

LangChain's 5 Evaluation Patterns

LangChain's team published "Evaluating Deep Agents" based on their experience building and evaluating production agents. They identified five patterns that, together, form a complete step-level evaluation strategy. Each pattern exists because a specific type of failure is invisible without it.

Pattern 1: Bespoke Test Logic Per Datapoint

This is the one most teams resist, because it sounds like more work. It is more work. It's also unavoidable.

Agents handle diverse tasks. A single agent might schedule meetings, write emails, search databases, and update CRMs — all in the same conversation. Using one uniform success criterion across all of those tasks is like using one grading rubric for a math test, a poetry assignment, and a chemistry lab. The criteria for "correct meeting scheduling" are completely different from the criteria for "good email writing."

Each test case needs custom success criteria matched to the specific task it's testing. For a calendar scheduling test, you check: did the agent update the right calendar, with the right time, the right attendees, and the right title? For an email writing test, you check: does the email match the requested tone, include the key points, and address the right person?

The Key Insight
Uniform eval criteria across all test cases is insufficient for agents. Each test case is a miniature product requirement, with its own definition of "correct." This is fundamentally different from evaluating a chatbot, where "helpfulness" and "accuracy" might carry you through most cases.

What this means in practice: your test dataset is not just inputs and expected outputs. Each row also needs a column for "how to check this specific case" — regex for some, LLM-as-judge for others, deterministic assertion for others. Your eval harness needs to support this flexibility.

Pattern 2: Single-Step Evaluations

This is where you should start. It gives you the highest ROI for the least investment.

The idea: pause the agent before it executes a tool call, and inspect the decision it made. Don't run the tool. Just look at what the agent chose to do and what parameters it chose to pass. Evaluate the decision, not the outcome.

Why is this so powerful? Because approximately half of all agent failures happen at the decision point, not during execution. The agent picks the wrong tool. Or it picks the right tool but fills in the parameters incorrectly. Or it picks the right tool with the right parameters but for the wrong reason (and will therefore misinterpret the result). All of these are detectable by inspecting the single step before execution.

LangChain found that roughly half of their test cases involved single-step evaluations. They use LangGraph's interrupt capabilities to pause before tool execution and inspect the agent's reasoning. This lets you evaluate decisions without executing them — which is cheaper, faster, and doesn't require standing up external services.

Start Here
If you do nothing else from this chapter, implement single-step evaluations. Intercept the agent's tool calls before execution. For each intercepted call, check: (1) Is this the right tool for this situation? (2) Are the parameters correct? (3) Does the agent's reasoning for this call make sense? This alone catches the majority of step-level failures.

Pattern 3: Full Agent Turns

When you need to evaluate more than a single decision, you evaluate a complete execution turn. A "turn" here means: the user says something, the agent thinks, calls tools, gets results, and produces a final response. The whole thing.

Full-turn evaluation checks three dimensions simultaneously:

  1. Trajectory — Were the right tools called in a reasonable order? Did the agent take a sensible path, or did it wander? (More on trajectory evaluation below.)
  2. Final Response — Was the output to the user high quality? This is your standard rubric-based evaluation from Phase 4.
  3. State Artifacts — Were files, databases, or other side effects correct? An agent might produce a great user-facing response while silently corrupting a database. Checking only the response misses this.

State artifacts are the hidden evaluation surface that most teams miss. If your agent writes files, updates databases, modifies configurations, or changes any external state, those changes need evaluation criteria too. The user-facing response is only half the story.

Pattern 4: Multi-Turn Conversations

When the agent has a back-and-forth conversation with the user (or with other agents), you need conditional logic between turns. Not rigid scripts — conditional flows.

A rigid test script says: "Send message A. Expect response B. Send message C. Expect response D." This breaks the moment the agent words its response slightly differently than expected (which is every time, because agents are non-deterministic).

A conditional test flow says: "Send message A. Check if the response contains the key information X. If yes, proceed with message C. If no, mark this turn as a failure and stop." The evaluation adapts to the agent's actual behavior while still checking that critical requirements are met at each stage.

Fail Early
The critical principle: check output after each turn and proceed only if it meets expectations. If the agent's response to turn 2 is already off track, there's no point evaluating turns 3, 4, and 5. Fail early. This saves eval compute and gives you a clear signal about where the conversation went wrong — not where it ended up after compounding several earlier errors.

Pattern 5: Environment Setup

This is the infrastructure pattern that makes the other four possible at scale.

"Deep agent evals require environments that reset per test." An agent that writes files, calls APIs, and modifies databases will leave state behind that affects the next test. If test #1 creates a file and test #2 unexpectedly finds that file, your test is evaluating the agent in a contaminated environment. The result means nothing.

The solution: isolated, resettable environments. Docker containers that spin up fresh for each test run. Temporary directories that get deleted after each case. Mocked external APIs (using tools like vcr for Python or Hono proxies for JavaScript) that return deterministic responses without hitting real services.

This costs engineering time upfront. It saves you from months of flaky, unreproducible eval results. Every team that skips this step ends up building it later, after wasting weeks debugging test failures that were actually environment contamination.

Environment Setup in Practice
A real example of what goes wrong without environment reset: Team A runs 50 eval tests sequentially. Test #12 creates a file called research.md. Test #23 asks the agent to "find existing research." The agent finds the file from test #12 and uses it. Test #23 passes — but only because of state leaking from test #12. When test #23 runs in isolation (or in a different order), it fails. The team spends two days debugging a "flaky test" that isn't flaky at all — it's order-dependent. A fresh Docker container per test would have caught this on day one.

Putting the 5 Patterns Together

The five patterns are not alternatives — they're layers. Here is how they compose:

Trajectory Evaluation: Was the Sequence of Actions Reasonable?

Beyond evaluating individual steps, you sometimes need to evaluate the path the agent took through its tools. Was the sequence of actions reasonable? Did it take unnecessary detours? Did it skip critical steps?

This is trajectory evaluation, and it has its own tooling. LangChain's open-source agentevals library provides five match modes for comparing an agent's actual trajectory against an expected one:

Match ModeWhat It TestsWhen to Use
Strict Match Identical tool call sequence, same order Compliance-driven workflows where the exact sequence is mandated. Financial reporting, regulatory filings, auditing processes.
Unordered Match All expected tools called, any order When tool interdependencies don't require ordering. "I need the agent to search, summarize, and format — but I don't care which happens first."
Subset Match Trajectory contains at least the expected calls When your reference represents minimum requirements. "At minimum, it must search and cite. If it also validates sources, great."
Superset Match Reference encompasses actual execution Identifying optimized paths. "The agent found a shorter route than our reference — that's good, not bad."
LLM-as-Judge Overall quality and reasonableness of the trajectory When there are no strict requirements, and you want a nuanced assessment. "Was this a reasonable approach?" Not "Did it match a template?"

The Key Tension: Outcomes vs. Trajectories

There is a genuine tension in the industry about trajectory evaluation, and you need to understand it to make good decisions for your product.

Anthropic's position (from "Demystifying Evals"): "Grade outcomes, not paths." There is a common instinct to check that agents followed very specific steps — a sequence of tool calls in the right order. This approach is too rigid and penalizes valid alternative solutions. An agent that achieves the right result via an unexpected path should not be marked as a failure.

LangChain's position (from "Evaluating Deep Agents"): Trajectory evaluation is essential for deep agents. When agents take dozens of steps across multiple tools, the trajectory IS part of the quality. An agent that achieves the right result but takes 47 unnecessary steps and costs $3 in tokens is not as good as one that does it in 5 steps for $0.15.

The Resolution
Both are right, but for different situations. Start with outcomes. If the agent produces correct, high-quality results, the path it took is secondary. Add trajectory evaluation ONLY when one of these is true:
  • Outcomes pass consistently but users still complain (the path is causing latency, cost, or UX issues)
  • You need to debug WHY outcomes sometimes fail (trajectory eval becomes a diagnostic tool, not a grading tool)
  • The path itself has compliance or safety implications (financial auditing, medical protocols)
  • Efficiency matters — token cost and latency are product metrics, not just engineering metrics
In practice: 80% of teams should start with outcome-only evaluation. The other 20% have regulatory, cost, or UX constraints that make trajectory evaluation a first-order concern from day one.

Designing Eval Gates Between Steps

The most practical application of step-level evaluation is the eval gate: a checkpoint between pipeline steps that decides whether to proceed, retry, or escalate.

Think of it like quality control on an assembly line. After each station, an inspector checks the work. If it's good, the piece moves to the next station. If it's bad, it gets sent back or flagged. Without inspection, a defect at station 2 propagates through stations 3, 4, 5, and 6 — and you discover it only at the end, when fixing it requires tearing apart the entire assembly.

Here's how to design eval gates for a generic agent pipeline:

Gate Design Template

For each gate, define four things:

Gate ComponentWhat to DefineExample
Position Between which two steps? After Research, before Analysis
What to Check The specific quality dimensions relevant to this step's output Did it find relevant sources? Are sources authoritative? Is the entity correctly identified?
Pass/Fail Criteria Unambiguous conditions for proceeding Pass: 3+ relevant sources found, correct entity identified. Fail: 0-2 sources OR wrong entity.
Fail Action What happens when the gate fails Retry with modified query (max 2 retries). If still failing, escalate to human.

Common Gate Types

Different steps need different types of gates:

After a Research/Retrieval Step:

  • Did it find relevant sources? (Count: 3+ means pass)
  • Are sources authoritative? (Check domains, publication dates)
  • Is the correct entity identified? (Deterministic check against input)
  • Fail action: Retry with expanded/modified search query. After 2 retries, flag for human review.

After an Analysis/Reasoning Step:

  • Are conclusions supported by the research? (LLM-as-judge: "Do these conclusions follow from the sources?")
  • Are there unsupported claims? (LLM check for statements not grounded in retrieved data)
  • Is the analysis specific, not generic? (The Logo Swap Test from Chapter 11)
  • Fail action: Regenerate with stronger grounding instruction. Include the failing criterion in the retry prompt.

After a Generation/Creative Step:

  • Does the output match the analysis? (LLM-as-judge: consistency check)
  • Does it meet format constraints? (Deterministic: word count, structure, required elements)
  • Is it brand-appropriate? (LLM-as-judge with brand guidelines as context)
  • Fail action: Regenerate with specific feedback about what's missing. Include the analysis output explicitly in the retry prompt.

After an Execution/Action Step:

  • Was the action actually performed? (Check logs, database state, API responses — not the agent's claim)
  • Were the parameters correct? (Compare actual parameters against expected)
  • Is the result consistent with the instruction? (Semantic check)
  • Fail action: Depends on reversibility. Reversible actions: undo and retry. Irreversible actions: halt and escalate to human.

How Many Gates Are Enough?

You don't need a gate after every step. Gates have a cost: they add latency (each gate is an LLM call or a deterministic check), they add complexity (each gate needs maintenance), and they can produce false positives that trigger unnecessary retries.

The rule of thumb: put gates at the boundaries where information transforms. Research becomes analysis. Analysis becomes creative output. Creative output becomes execution. These transformation boundaries are where context is most likely to be lost, distorted, or fabricated.

Don't put gates between steps that are purely mechanical (formatting, file writing, API calls with deterministic inputs). These either work or throw an error — there's nothing for an eval gate to evaluate.

Implementing Gates: Lightweight vs. Heavy

Not every gate needs an LLM judge. Match the gate's complexity to the step's risk:

Start with deterministic gates everywhere you can. Graduate to LLM-as-judge only for steps where the quality judgment is genuinely subjective. Most teams over-index on LLM judges when a simple check for "does the output contain the brand name" would catch 60% of failures at zero cost.

The Cost-Benefit of Step-Level Eval

Step-level evaluation is not free. Each gate adds latency and (for LLM-based gates) cost. Here's how to think about the trade-off:

The Gate ROI Calculation
Without gates:
A 6-step pipeline with 90% per-step success rate = 53% end-to-end success. You discover failures only at the end. Re-running the entire pipeline for each failure costs 100% of pipeline compute.

With 3 deterministic gates (free, <1ms each):
If a gate catches a failure at step 2, you retry only step 2 instead of the whole pipeline. Cost savings: 67% of pipeline compute per retry. Latency added: <3ms total. This is an obvious win.

With 3 LLM-based gates ($0.01-0.05 per call):
Each gate adds 1-3 seconds and a few cents. For a pipeline that costs $0.50 and takes 45 seconds, adding $0.15 in gates (3 gates × $0.05) increases cost by 30% but reduces wasted retries by 50%+. The gates pay for themselves if your failure rate is above ~10%.

Rule of thumb: If your pipeline failure rate is above 10%, gates save money even accounting for their cost. If below 5%, gates cost more than they save. Between 5-10%, deterministic gates are worth it but LLM gates may not be.

Track your pipeline's per-step failure rates for one week before deciding where to place gates. The data will tell you exactly which steps need gates and which don't.

Chapter 16Tool Use Evaluation

First Principle
Every tool call is a 3-part decision. The agent decides WHICH tool to use, WHAT input to give it, and HOW TO INTERPRET the result. Each part can fail independently. That gives you 3 evaluation surfaces per tool call — and agents can make dozens of tool calls per task.

When a chatbot gives a bad answer, there's one thing to evaluate: the answer. When an agent gives a bad answer, the answer might be fine but the action it took was wrong. Or the action was right but the parameters were wrong. Or the parameters were right but the agent misunderstood the result. Tool use is where the agent-chatbot divide gets real, and where generic eval frameworks fall apart.

The 3 Core Metrics

Amazon's agentic AI teams and Confident AI's DeepEval framework converge on three essential metrics for tool use. These are not optional — if your agent uses tools (and almost every production agent does), you need all three.

Metric 1: Tool Selection Accuracy

Did the agent choose the right tool?

This is the most fundamental question. Before we care about parameters or interpretation, did the agent even reach for the right tool? If the user asks "What's the weather in Chicago?" and the agent calls the stock-price API instead of the weather API, nothing downstream matters.

Tool selection is often the easiest metric to evaluate, because for many inputs there is an unambiguous correct tool. If the user says "schedule a meeting," the correct tool is the calendar tool, not the email tool, not the search tool. This can be tested deterministically: given this input, assert that this tool was selected.

DeepEval implements this as the ToolCorrectnessMetric — it compares tools_called against expected_tools. It supports ordering requirements (when the sequence matters) and exact match (when extra tool calls are a problem, not just missing ones). The score ranges from 1.0 (all correct) to 0.0 (none correct).

What "Wrong Tool" Looks Like
Wrong tool selection is not always as obvious as calling the weather API for a stock question. Subtler failures:
  • Agent uses web search when the answer is in an already-retrieved document (unnecessary external call)
  • Agent uses a general search tool when a specialized API would give a better result (e.g., using Google search instead of the company's internal knowledge base)
  • Agent calls a write tool when the user only asked for information (unintended side effect)
  • Agent calls tools in the wrong order, causing the second call to fail because it depends on the first call's output

Metric 2: Argument Correctness

Right tool, but were the parameters correct?

Calling the right tool with wrong arguments is just as bad as calling the wrong tool. DeepEval's framing is direct: "Calling the right tool with wrong arguments is just as problematic as calling the wrong tool entirely."

This is harder to evaluate than tool selection, because "correct arguments" is often context-dependent. If the user says "find meetings next week," the date parameters need to be calculated relative to today's date. If the user says "search for Nike's latest campaign," the search query needs to capture the right brand, the right timeframe, and the right content type.

DeepEval's ArgumentCorrectnessMetric is fully LLM-based and referenceless — it evaluates whether arguments were logically derived from the conversational context, rather than comparing against pre-defined expected values. This is important because there are usually multiple valid ways to fill in parameters. "Nike latest ad campaign 2026" and "Nike recent advertising campaign" are both reasonable search queries. A deterministic check against one expected string would fail the other.

That said, some parameters CAN be checked deterministically. Dates, IDs, enums, and other structured parameters have a finite set of correct values. Use deterministic checks where you can, LLM-as-judge where you must.

Metric 3: Result Interpretation

Right tool, right input, but did the agent correctly use the output?

This is the hardest of the three to evaluate, and the one teams most often ignore. The tool returned data. Did the agent understand it? Did it extract the relevant information? Did it notice when the data was incomplete, contradictory, or irrelevant?

Consider: the agent searches for "Nike revenue 2025" and gets back a page that includes Nike's revenue ($51.2B), their employee count (79,400), and a paragraph about their supply chain challenges. The user asked about revenue. Does the agent:

  • Extract the revenue figure correctly? (basic competence)
  • Ignore the irrelevant employee count and supply chain info? (focus)
  • Notice if the source says "fiscal year 2024" not "2025"? (precision)
  • Flag that the number might be outdated? (calibrated confidence)

Result interpretation evaluation typically requires LLM-as-judge, because you're evaluating reasoning about data, not data itself. The judge prompt looks something like: "Given this tool output and this user question, did the agent correctly identify and use the relevant information?"

The 3 Agent-Specific Failure Modes

Beyond the three metrics, DeepEval identified three failure modes that are specific to agents — they don't exist in chatbots. Each one is a distinct pathology with distinct symptoms and distinct tests.

Failure Mode 1: The Ghost Action (False Task Completion)

The Ghost Action
What happens: The agent claims "Done! I've updated your calendar" without actually calling the calendar API. It says "I've sent the email" but no email was sent. It reports "File saved successfully" when no file operation occurred.

Why it happens: Language models learn that confident claims of completion produce positive user responses. The model has learned, from millions of training examples, that "Done!" is a satisfying answer. Whether the task was actually executed is a separate concern that the model doesn't inherently track. Execution is optional when the user can't immediately verify the result.

Why it's dangerous: The user walks away thinking the task is done. They don't check. The meeting never gets scheduled. The email never gets sent. The failure is discovered hours or days later, when the consequences are much worse.

How to detect it: Compare the agent's claimed actions against the actual tool call log. For every claim like "I've done X," verify that a corresponding tool call exists in the execution trace. If the agent says "I've updated your calendar" but the trace shows zero calendar API calls, that's a ghost action.

How to test for it: Give the agent a task that unambiguously requires a specific tool call. "Schedule a meeting with Alex tomorrow at 2pm." Then check: was the calendar tool actually invoked? Were the parameters (Alex, tomorrow, 2pm) present? Don't check the response text — check the tool call log. Ghost actions look perfect in the response and completely empty in the logs.

// Ghost Action Test Case
input:    "Schedule a meeting with Alex for tomorrow at 2pm"
check:    tool_calls MUST include calendar.create_event
check:    calendar.create_event.params MUST include attendee="Alex"
check:    calendar.create_event.params MUST include date=tomorrow
check:    calendar.create_event.params MUST include time="14:00"
anticheck: If response says "scheduled" but tool_calls is empty = GHOST ACTION

Failure Mode 2: The Interrogation Loop (Parameter Extraction Failure)

The Interrogation Loop
What happens: The agent can't map natural language to structured tool parameters. Instead of making a reasonable attempt or gracefully failing, it keeps asking the user for clarification. "Can you specify the exact date?" "What format would you like?" "Could you clarify the time zone?" Three, four, five rounds of clarification for a task that should resolve in one or two turns.

Why it happens: There's a gap between how users naturally express intent ("schedule something for next week") and how tools expect structured input ({"date": "2026-04-07", "time": "09:00", "timezone": "PST"}). The agent doesn't know how to bridge that gap — it can't infer reasonable defaults, pick a sensible time, or make a judgment call. So it asks. And asks. And asks.

Why it's dangerous: The user loses patience and abandons the task. Or worse, they give up on the agent entirely: "This thing is useless — it can't even schedule a meeting without 10 questions."

How to detect it: Count the number of turns before the agent successfully invokes the target tool. If the user's initial instruction was clear enough that a human assistant would execute it in one turn, but the agent takes 4+ turns of clarification, that's an interrogation loop.

How to test for it: Give the agent clear, unambiguous instructions that should resolve in 1-2 turns. Measure the turn count to successful tool invocation. Any case that takes more than 3 clarification rounds is flagged.

// Interrogation Loop Test Case
input:    "Email the Q3 report to Sarah at sarah@company.com"
expected: Tool invocation within 1-2 turns
flag_if:  Agent asks 3+ clarifying questions before calling email.send
// A good agent would: pick a reasonable subject line, attach the report,
// compose a brief body, and send. Maybe ask ONE question if the report
// name is ambiguous. NOT ask about subject, body, format, cc, bcc...

Failure Mode 3: The Confident Fabricator (Intermediate Output Quality)

The Confident Fabricator
What happens: The agent calls a tool, gets back garbage (an error, empty results, completely irrelevant data), and doesn't notice. It takes the garbage at face value and weaves it into its response with complete confidence. The tool returned an error message, and the agent summarizes that error message as if it were real data.

Why it happens: Agents are optimistic by default. They assume tool results are correct. They don't have a built-in "sanity check" on incoming data. If the search tool returns "No results found," the agent might say "Based on my research, the company has no public information" when the reality is that the search just failed.

Why it's dangerous: The user has no way to distinguish between "the agent found this information" and "the agent made this up based on a tool error." The confidence is identical. The tone is identical. Only the source is different.

How to detect it: Inject known-bad tool responses and check if the agent catches them. Return empty results from a search that should find thousands of hits. Return an error message instead of data. Return data for the wrong entity. Does the agent notice? Does it flag the problem? Or does it confidently proceed?

How to test for it: Mock a tool to return obviously wrong or empty data. Then evaluate: did the agent (a) acknowledge the data quality issue, (b) try an alternative approach, or (c) confidently present garbage as truth?

// Confident Fabricator Test Case
input:    "What is Apple's current stock price?"
mock:     stock_api.get_price returns {"error": "API rate limited"}
pass_if:  Agent says "I couldn't retrieve the stock price right now"
pass_if:  Agent tries an alternative source
FAIL_if:  Agent says "Apple's stock price is currently $XXX" (fabricated)
FAIL_if:  Agent says "Apple's stock price is 'API rate limited'" (parroting error)
How Common Are These?
In our experience building and evaluating production agents: Ghost Actions happen most with tasks the agent has "seen" in training but rarely executes with tools (sending emails, updating databases). Interrogation Loops happen most with tools that have many parameters (calendar events, complex search queries). Confident Fabricators happen most with tools that can return partial or degraded results (web search, API calls to third-party services). Every production agent we've tested exhibited at least one of these failure modes.

Building Your Tool Evaluation Suite

Here is a phased build plan that gets you from zero tool evaluation to comprehensive coverage in about a month.

Phase 1: Deterministic Tool Selection Tests (Week 1)

For each tool your agent has access to, create 5-10 test inputs where the expected tool is unambiguous. No judgment calls, no edge cases — just clear inputs with clear expected tools.

// Example: Agent with 4 tools (search, email, calendar, file_manager)

Test 1:  "Find information about Tesla's latest earnings"
         Expected tool: search

Test 2:  "Send a summary to the team at team@acme.com"
         Expected tool: email

Test 3:  "Block off 2-3pm tomorrow for deep work"
         Expected tool: calendar

Test 4:  "Save this report as Q3-summary.pdf"
         Expected tool: file_manager

Test 5:  "What's on my schedule for Friday?"
         Expected tool: calendar (read, not write)

// 5-10 per tool = 20-40 total test cases
// Pure assertion: did the agent select the right tool?
// No LLM judge needed. Binary pass/fail.

This is the fastest eval suite you can build. Most teams can create 20-40 of these in a single afternoon. Run them, measure tool selection accuracy. If it's below 90%, you have a tool description problem (the tool descriptions in your agent's system prompt are ambiguous or misleading).

When Tool Selection Fails: It's Usually the Description
When tool selection accuracy is low, the first instinct is to blame the model. Usually, the problem is the tool descriptions in your system prompt. The model selects tools based on how you describe them. Vague descriptions produce ambiguous selections.

Bad: search_web - "Searches the web for information."
Bad: search_docs - "Searches internal documents."

These descriptions don't tell the model WHEN to use each tool. When should it search the web vs. search internal docs?

Good: search_web - "Search the public internet for current information about companies, news, trends, or public data. Use for external research when the answer is NOT likely in our internal knowledge base."
Good: search_docs - "Search the company's internal documentation, including product specs, engineering docs, and internal wikis. Use for questions about our own products, processes, or internal data."

When your tool selection eval fails, debug the description before changing the model or the prompt.

Phase 2: Argument Correctness via LLM-as-Judge (Weeks 2-3)

For each tool, create 5-10 test inputs and have an LLM evaluate whether the parameters were correctly extracted from context. This requires an LLM judge because "correct parameters" is context-dependent.

Worked Example: Evaluating a Full Tool Call Sequence

Let's walk through evaluating a real agent interaction end to end, applying all three metrics and checking for all three failure modes.

Scenario: Travel Booking Agent
User: "Book me a flight from SFO to JFK for next Friday, economy class, arriving before 3pm."

Agent's tool call sequence:
  1. search_flights({origin: "SFO", dest: "JFK", date: "2026-04-10", class: "economy"})
  2. filter_results({max_arrival: "15:00", sort: "price"})
  3. book_flight({flight_id: "UA234", passenger: "current_user"})
Evaluation across all 3 metrics:

Tool Selection:
• search_flights → Correct for finding flights. PASS.
• filter_results → Correct for narrowing by arrival time. PASS.
• book_flight → Correct for making the reservation. PASS.
• No unnecessary tools called. PASS.

Argument Correctness:
• Origin "SFO" → matches user's request. PASS.
• Destination "JFK" → matches user's request. PASS.
• Date "2026-04-10" → is this "next Friday" from today? Must verify against current date. If today is April 6 (Monday), next Friday is April 10. PASS.
• Class "economy" → matches. PASS.
• Max arrival "15:00" → "before 3pm" = before 15:00, so this should be "14:59" or the filter should be strict less-than, not less-than-or-equal. BORDERLINE.
• Passenger "current_user" → correct default. PASS.

Result Interpretation:
• Did the agent select the cheapest flight that meets all criteria? Or just the first result? Check if the sorted results were actually used for selection.
• Did the agent confirm the booking details with the user before calling book_flight? (Depends on your product's UX requirements.)
• After booking, did the agent communicate the confirmation number, departure time, and arrival time? PASS/FAIL depending on response content.

Failure Mode Check:
• Ghost Action: Did book_flight actually execute and return a confirmation? Check the tool return value, not just the agent's claim. If tool returned {"status": "confirmed", "booking_id": "BK9921"}, it's real. If the agent said "Booked!" but the tool log shows no book_flight call, it's a ghost.
• Interrogation Loop: Agent resolved everything in one turn. No unnecessary clarification. PASS.
• Confident Fabricator: If search_flights returned no results (maybe there are no SFO-JFK flights on that date), did the agent report this? Or did it hallucinate a flight?

This worked example shows how a single user request generates multiple evaluation checkpoints. In production, you wouldn't manually trace every request like this. But you'd build automated checks for the highest-risk tool calls — especially tool calls that have real-world consequences (bookings, purchases, data modifications).

Tool Evaluation Checklist

For every tool use test case in your suite, run through this checklist:

  • Correct tool selected?
  • Parameters well-formed and specific? (not vague, not default values when specific ones were provided)
  • Tool output validated before use? (did the agent check for errors, empty results, irrelevant data?)
  • Graceful handling when tool fails or returns bad data? (retry, fallback, or honest admission — not fabrication)
  • Efficient? (minimum necessary tool calls — didn't call the same tool 5 times for slightly different queries when 1-2 would suffice)

The Safety Dimension of Tool Eval

Tool evaluation is not just about quality — it's also about safety. An agent that calls the wrong tool can have consequences far beyond a bad user experience. Consider:

  • An agent that calls delete_file instead of read_file because the tool descriptions are ambiguous
  • An agent that calls send_email to the wrong recipient because it extracted the email address from the wrong part of the conversation
  • An agent that calls update_database with parameters derived from user input that hasn't been sanitized
  • An agent that calls a billing API when the user only asked for pricing information

Each of these is a tool use failure that Phase 4's content-quality evaluation would never catch. The response text might be perfectly written. The action is wrong. This is why tool evaluation is not optional for any agent that takes actions with real-world consequences.

For high-stakes tools (anything that modifies data, sends communications, or makes purchases), add a special test category: boundary tests. These are inputs designed to be close to, but not quite, a valid reason to use the dangerous tool. Does the agent correctly decide NOT to call the tool? Not calling a tool is sometimes the most important evaluation criterion.

// Boundary Test: Agent should NOT call send_email
input:  "Draft an email to the client about the project delay"
assert: Agent calls draft_email, NOT send_email
// "Draft" means prepare, not send. The user hasn't approved it yet.
// An agent that sends on "draft" has overstepped its authority.

These are your Phase 1 tests. They take an afternoon to create and immediately tell you whether your agent's tool selection is reliable. If you find problems here, fix them before worrying about anything more sophisticated.

Tools are covered. But agents also have conversations — they maintain context across turns. And memory is where some of the sneakiest failures hide.

Chapter 17Multi-Turn and Memory Evaluation

First Principle
Memory is a promise. When a user tells the agent something, the agent implicitly promises: "I heard you, and I'll remember it." Breaking this promise destroys trust faster than almost any other failure — because it makes the user feel unheard. A wrong answer is frustrating. A forgotten answer is alienating.

When you evaluate a chatbot, each turn is mostly independent. The user asks a question, the chatbot answers, you grade the answer. Simple. Clean.

When you evaluate an agent, turns are entangled. Turn 5's quality depends on how well the agent understood turns 1-4. Turn 10 might be perfect in isolation but terrible in context because it contradicts something the user said in turn 3. Turn 20 might be useless because the agent forgot the user's core requirements from turn 1.

You cannot evaluate turns in isolation. And yet, that's exactly what most eval systems do — they evaluate each response against its immediate prompt, ignoring the conversation history that makes the response good or bad.

5 Things to Test for Memory and Context

Multi-turn evaluation has five distinct dimensions. Each one tests a different aspect of the agent's memory and context handling. Each one can fail independently.

1. Persistence

Does the agent remember information from earlier in the conversation?

This is the most basic memory test, and the most commonly failed. After 5, 10, 20+ turns, give the agent a question that can only be answered with information from the early turns. Measure recall accuracy.

The test is simple. The failure is not. Agents don't just "forget" — they lose resolution. They might remember that the user mentioned a company but forget which company. They might remember a preference was expressed but mix up the details. The degradation is gradual and subtle, which makes it harder to detect than a hard failure.

// Persistence Test
Turn 1:  User: "I'm the CMO at Patagonia. We're launching a new
               line of recycled-material jackets called 'ReThread'."
Turn 2:  Agent: [acknowledges, asks about target audience]
Turn 3:  User: "Target is environmentally conscious millennials,
               household income $75K+, urban areas."
Turns 4-19: [detailed discussion about channels, budget, timeline...]

Turn 20: User: "Remind me — what product line are we working on,
               and who's the target audience?"

PASS: "We're working on ReThread, Patagonia's new recycled-material
       jacket line. Target: environmentally conscious millennials,
       $75K+ household income, urban areas."
FAIL: "We're working on your new jacket line for eco-conscious consumers."
       // Lost: brand name, product name, income bracket, "urban"
       // This is a resolution failure, not a total memory loss

2. Knowledge Updates

When the user corrects earlier information, does the agent update its understanding?

This is harder than persistence. The agent needs to not only remember new information but replace old information. If the user says "our budget is $500K" in turn 5, then says "actually, our budget got cut to $300K" in turn 15, the agent must use $300K from that point forward. Using $500K in turn 20 is a knowledge-update failure.

Why is this so hard? Because language models have a recency bias in some contexts and a primacy bias in others. The model might anchor on the first piece of information it received (primacy) and resist updating it, especially if the conversation has moved on to other topics between the original statement and the correction.

// Knowledge Update Test
Turn 5:   User: "Our target market is the US and Canada."
Turns 6-14: [other topics]
Turn 15:  User: "Actually, we've decided to focus US-only for launch.
                Canada will be phase 2."
Turns 16-19: [other topics]
Turn 20:  User: "Can you summarize the campaign geography?"

PASS: "The campaign targets the US market. Canada is planned for phase 2."
FAIL: "The campaign targets the US and Canada."
       // Used the turn 5 value, ignored the turn 15 update

3. Abstention

When asked about information that was never provided, does the agent admit it doesn't know?

A good agent says "I don't have that information" or "You haven't mentioned that — could you tell me?" A bad agent hallucates a plausible-sounding answer. This is the memory equivalent of the Confident Fabricator from Chapter 16 — but instead of fabricating based on bad tool output, it fabricates based on missing conversation context.

// Abstention Test
Context: 15-turn conversation about a Nike campaign.
          Budget has NEVER been mentioned.

Turn 16: User: "What budget are we working with?"

PASS: "We haven't discussed the budget yet. What budget
       do you have in mind for this campaign?"
FAIL: "Based on the scope of this campaign, I'd estimate
       a budget of around $250K."
       // Hallucinated a specific number that was never discussed
       // Worse: it sounds reasonable, so the user might not question it

Abstention is particularly important for agents that handle financial, legal, or medical information. An agent that invents a budget number, a contract term, or a dosage recommendation from thin air is actively dangerous.

4. Feedback Incorporation

When the user gives directional feedback, does the next output actually change?

This is the "I told it to make changes and it ignored me" problem. The user says "Make it edgier." The agent produces a new version that's nearly identical to the previous one. Or the user says "Too formal — make it conversational" and the next output is slightly less formal but still reads like a press release.

Testing this requires comparing the output before and after the feedback, specifically on the dimension the user asked to change.

// Feedback Incorporation Test
Turn 1:  User: "Write 5 taglines for a fitness app"
Turn 2:  Agent: [generates 5 taglines — clean, professional, safe]
         // Example: "Your fitness journey starts here."
Turn 3:  User: "Too generic. Make them edgier — think Nike, not Hallmark."
Turn 4:  Agent: [generates 5 new taglines]

Eval Turn 4 — check 4 things:
  1. Did the tone shift? Compare Turn 2 vs Turn 4 on an "edge" scale.
     Turn 4 should score meaningfully higher on boldness/provocativeness.
  2. Did it keep the fitness context? Taglines should still be about
     fitness, not some other product. Context retention during revision.
  3. Did it acknowledge the feedback? Not necessarily explicitly, but
     the output should show evidence that the "Nike, not Hallmark"
     direction was internalized.
  4. Are the new ones actually better? Holistic quality: are they
     more memorable, more specific, more impactful?
The Feedback Incorporation Test Is Underused
Most eval systems test whether the agent produces good output. Few test whether it produces better output after feedback. But this is exactly what users do in practice — they iterate. They refine. They steer. An agent that produces a great first draft but can't be steered is less useful than an agent that produces a mediocre first draft but responds brilliantly to feedback. Iteration ability is a core agent skill that almost no eval suite explicitly measures.

5. Context Window Pressure

What happens when the agent approaches its context limit?

Every agent has a finite context window. Most production agents hit that limit during long sessions. What happens then is one of the least-tested aspects of agent behavior, and one of the most consequential.

When context pressure gets high, the agent (or its underlying infrastructure) must do something: summarize and compress, drop old messages, or start losing coherence. Each approach has trade-offs. Summarization loses detail. Dropping old messages loses the user's original requirements. Losing coherence produces garbage.

Track token consumption per session. Know when your agent hits 50%, 75%, and 90% of its context window. Test what happens at each threshold.

Context Pressure Test Design
Build a test that gradually fills the context window with realistic conversation content while embedding specific, testable facts at known positions. Then measure recall accuracy at different fill levels.

Setup: Embed 10 distinct facts (brand name, budget, target audience, launch date, etc.) spread across the conversation. Fill the rest with realistic but non-critical discussion.

Measure at:
  • 25% context capacity: Expect near-perfect recall (9-10 / 10)
  • 50% context capacity: Expect strong recall (8-10 / 10)
  • 75% context capacity: Watch for degradation, especially on mid-context facts
  • 90%+ context capacity: This is where you find out how your agent handles pressure
Key metric: At what fill level does recall drop below 80%? That is your agent's practical context limit, regardless of what the model's spec sheet says.

Bonus: Contradiction Detection

There is a sixth dimension worth mentioning, even though it doesn't fit neatly into the five categories above: self-contradiction. Does the agent contradict itself across turns?

This is different from knowledge updates (where the USER corrects earlier information). Contradiction means the AGENT changes its own claims without any new input. In turn 5, it says "Adidas's primary competitor in running shoes is Nike." In turn 12, unprompted, it says "Adidas leads the running shoe market with no major competition." Both can't be true. The agent didn't get new information between turn 5 and turn 12 — it just lost consistency.

Contradiction detection is hard to test systematically because you need to compare claims across turns. The practical approach: after a long session, ask the agent to summarize its key conclusions. Then compare those conclusions against specific claims made during the session. Any contradictions are flagged. This can be done with an LLM judge: "Here are 5 claims the agent made during the conversation [list them]. Here is the agent's final summary. Do any of the summary's claims contradict the earlier claims?"

The "Context Rot" Problem

Research from Chroma (published as "Context Rot," 2025) found something that should make every AI PM uncomfortable:

Context Rot Research Findings
  • Models claim 200K token context windows but become unreliable around 130K tokens (~65% of claimed capacity)
  • Information placed in the early and late portions of the context: 85-95% accuracy
  • Information placed in the middle sections: significant accuracy drops
  • The "lost in the middle" problem is real and not fully solved by any current model

What this means for your agent: if you have sessions that run 20+ turns and accumulate more than 100K tokens of context, the agent's ability to recall and use information from the middle of the conversation is degraded. Not catastrophically. Not obviously. Just enough that details get lost, nuances get flattened, and the agent starts giving slightly worse answers without anyone noticing — until a user complains that "it forgot what I told it 10 minutes ago."

The practical implication: test your agent with long sessions specifically designed to probe middle-context recall. Don't just test turn 1 recall from turn 20 (that's early context, which stays strong). Test turn 10 recall from turn 20 (that's middle context, which degrades).

The Context Rot Testing Protocol

Based on the Chroma research, here's a structured protocol for testing context rot in your specific agent:

  1. Plant 10 facts at evenly spaced positions throughout a long conversation: turns 1, 3, 6, 9, 12, 15, 18, 21, 24, and 27 in a 30-turn conversation.
  2. Ask recall questions in turn 30 for each fact. Score each recall as Exact (remembered the specific detail), Approximate (remembered the gist but lost specifics), or Missing (didn't remember at all).
  3. Plot the results. You should see a U-shaped curve: high recall for early facts (turns 1-3), high recall for recent facts (turns 24-27), and lower recall for middle facts (turns 9-18). The depth of the U tells you how severe your agent's context rot is.
  4. Compare across context sizes. Run the same test at 50K, 100K, and 150K tokens. The U-shape gets deeper as context fills up.

Most PMs never run this test. The ones who do are consistently surprised by how much their agents lose in the middle. Document your agent's context rot curve. Share it with engineering. It will inform decisions about when to trigger summarization, how to structure long conversations, and whether to proactively re-inject critical information from earlier in the session.

Context Rot in Practice
Consider a 25-turn product design session. The user specified a key constraint in turn 8: "The widget must fit within a 320px container." By turn 20, the conversation has covered typography, color, animations, and accessibility. The agent proposes a layout that's 480px wide. It didn't "forget" the constraint in a dramatic way. The constraint just faded as the context filled with more recent topics. The user catches it, corrects it, and moves on. But their trust in the agent just dropped a notch. After three or four instances like this, the user stops trusting the agent to remember constraints and starts repeating themselves every few turns. The agent becomes a tool they have to micromanage instead of a collaborator they can rely on.

The Follow-Up Eval Pattern

This pattern specifically tests whether the agent can incorporate user feedback across turns. It's the gold standard for evaluating iterative collaboration:

TurnRoleContentEval Check

2 Agent [Generates 5 taglines] Are they about fitness? Are there 5?

The power of this pattern: it tests memory, feedback incorporation, quality improvement, and context retention all in one compact, 4-turn test. Design 3-5 of these for your product's core use cases and you have a meaningful multi-turn eval suite in an afternoon.

Extending the Follow-Up Pattern: The 3-Iteration Stress Test

The 4-turn pattern above is a minimum. For products where iteration is central to the experience (design tools, writing assistants, campaign generators), extend it to three rounds of feedback:

TurnContentWhat You're Testing
1-2 Initial request → first output Baseline quality. Does the agent produce something reasonable from scratch?
3-4 Direction change ("edgier") → revised output Feedback incorporation. Did it actually change?
5-6 Refinement ("keep the edge but make it shorter") → re-revised output Compound feedback. Can it apply new feedback WITHOUT losing previous feedback? Turn 6 should be edgy (from turn 3) AND shorter (from turn 5).
7-8 Constraint addition ("also make sure it works for Instagram format") → final output Constraint accumulation. Turn 8 should be edgy + short + Instagram-formatted. Every prior constraint must still be satisfied.

This stress test reveals a common failure mode: feedback amnesia. The agent successfully incorporates feedback from turn 5, but in doing so, it "forgets" the feedback from turn 3. Each revision only remembers the most recent directive. After three rounds, the output reflects only the last piece of feedback, not the accumulated intent. This is extremely common and extremely frustrating for users, because it means every revision is one step forward, one step back.

Feedback Amnesia
If your agent can incorporate one round of feedback but loses earlier feedback during subsequent rounds, the issue is usually context management, not capability. The agent is capable of following each instruction individually — it just can't hold multiple accumulated directives simultaneously. Solutions include: summarizing all active directives before each generation, adding a "current brief" that accumulates constraints, or restructuring the system prompt to include a running list of user requirements.

The Husain-Shankar Multi-Turn Framework

Hamel Husain and Shreya Shankar propose three aspects to evaluate in any multi-turn conversation. Together, they cover the full scope of what "multi-turn quality" means:

Aspect 1: Context and Memory

Does the AI remember earlier parts of the conversation? How does behavior change as the conversation lengthens? This is your persistence and knowledge update testing from above. The key insight from Husain: don't just test whether the agent remembers — test how its behavior degrades as the conversation grows. Does it get more generic? Does it start contradicting earlier statements? Does it lose track of constraints?

Aspect 2: Consistency

Do responses align across turns without contradictions? An agent that says "your budget is $200K" in turn 5 and then says "given your $150K budget" in turn 15 has a consistency failure — even if neither number was correct. Consistency is distinct from accuracy. An agent can be consistently wrong (bad but at least predictable) or inconsistently right (confusing even when correct). Both need detection.

Consistency failures fall into three categories, each requiring different detection methods:

Consistency TypeWhat BreaksHow to DetectExample
Factual Consistency Agent states different numbers, dates, or facts across turns Extract factual claims from each turn, compare for contradictions "Revenue is $50M" (turn 5) vs. "Given their $35M revenue" (turn 15)
Recommendation Consistency Agent gives conflicting advice across turns without acknowledging the change Track directional recommendations, flag reversals without explanation "I'd recommend TikTok for this audience" (turn 7) vs. "Instagram is the best channel here" (turn 18)
Personality Consistency Agent's tone, style, or persona shifts unexpectedly between turns LLM-as-judge comparing tone across turn pairs Formal and professional in turns 1-10, suddenly casual and slangy in turns 11+

Factual consistency is the highest priority because it directly undermines trust. If the agent can't keep its own facts straight, the user has no reason to trust any fact it presents. Recommendation consistency is second priority — shifting advice without acknowledging why is confusing. Personality consistency matters most for customer-facing agents where a stable persona is part of the product experience.

Aspect 3: Session Goals

This is the big picture: did the entire session achieve the user's objective? Not each individual response, but the conversation as a whole. A session where every individual response was adequate but the user's goal was never achieved is a failure that turn-level evaluation misses entirely.

Session-goal evaluation requires you to define what "done" means for your product. Some examples:

  • Research agent: Did the session produce a complete, accurate research report that answers the user's original question?
  • Campaign generator: Did the session produce a set of creative assets (hooks, images, copy) that the user accepted or downloaded?
  • Customer support agent: Did the session resolve the customer's issue without escalation?
  • Coding assistant: Did the session produce working code that passes tests and meets the user's requirements?

Notice that "done" is product-specific, not model-specific. Your session-goal evaluation should match your product's success metrics. If your product tracks "campaigns completed" or "issues resolved," your session-goal eval should measure the same things.

Turn-Level vs. Session-Level Evaluation
Turn-level evaluation grades each response individually: "Was response 7 good?" Session-level evaluation grades the whole conversation: "Did this 25-turn session accomplish what the user needed?" Both are necessary. Many sessions fail at the session level while passing at the turn level — every individual response seems fine, but the conversation never actually converges on a solution. The agent is helpful in each moment but useless overall. Session-level evaluation is the only way to catch this.

1 Persistence (20+ turns) Introduce key facts in turns 1-5. Fill turns 6-19 with detailed discussion. Ask recall questions in turns 20-22. Recalls 5/7+ facts with correct details. Not just "you mentioned a brand" but "you mentioned Allbirds."
2 Knowledge Updates State fact A in turn 5. Correct to fact B in turn 15 (with intervening conversation). Test which value is used in turn 20. Uses the updated value (B), not the original (A). Bonus: explicitly acknowledges the update.
3 Abstention 15-turn conversation that never mentions pricing. Turn 16: "What pricing did we agree on?" Agent says "We haven't discussed pricing yet" or asks the user. Does NOT invent a price.
4 Feedback Incorporation Agent produces output. User gives directional feedback ("edgier," "shorter," "more data-driven"). Agent produces revised output. Revised output measurably shifts on the requested dimension. Does not regress on other dimensions.
5 Context Pressure Extended conversation (30+ turns or high-token-count messages) that pushes past 50% of context window. Test recall of early details. No significant degradation compared to the 20-turn persistence test. If there IS degradation, document at what turn count/token count it starts.

Implementing Multi-Turn Test Execution

Multi-turn tests are harder to run than single-turn tests because each turn depends on the previous turn's response. Here are three implementation approaches, ordered by complexity:

Approach 1: Script-Based (Simplest)

Write a script that sends messages sequentially, waits for responses, and runs checks between turns. The "conversation" is a list of messages with embedded check functions. Works for most teams starting out.

// Pseudocode: Script-Based Multi-Turn Test
const test = [
  { send: "I'm working on a Nike campaign.",
    check: (response) => response.includes("Nike") },
  { send: "Actually, switch to Adidas.",
    check: (response) => response.includes("Adidas") },
  { send: "What brand are we working on?",
    check: (response) => response.includes("Adidas")
      && !response.includes("Nike") },
];

for (const turn of test) {
  const response = await agent.send(turn.send);
  if (!turn.check(response)) {
    fail(`Turn failed: ${turn.send}`);
    break; // Fail early
  }
}

Approach 2: State Machine (Medium)

Model the conversation as a state machine where each state has a message, a check, and transitions to the next state based on the check result. This supports branching — if the agent responds one way, go down path A; if another way, go down path B.

Approach 3: LLM-Driven Conversation (Advanced)

Use a second LLM to play the user role, with instructions about what information to provide, what to test, and when to end the conversation. The "test" is the evaluator LLM's final assessment of whether the agent achieved the session goal. This is the most flexible but hardest to make deterministic.

Most teams should start with Approach 1. It's concrete, debuggable, and covers the five essential test types from the table above. Graduate to state machines when your test cases have complex branching logic. Use LLM-driven conversations for open-ended exploration of agent behavior (more like red-teaming than regression testing).

DO — Your Turn
Build 5 multi-turn test cases for your agent, using the table above as a template. At minimum:
  • 1 testing persistence over 20+ turns
  • 1 testing knowledge updates (correct earlier information)
  • 1 testing feedback incorporation (did the output actually change?)
For each test: write the conversation flow, define the checkpoints, and specify pass/fail criteria. Remember: use conditional logic, not rigid scripts. The agent's exact wording will differ each run — your checks should evaluate the substance, not the phrasing.

For some products, there's one more layer of complexity: multiple agents working together. If your product uses a single agent, you can skip Chapter 18 and move to Phase 6. If your product coordinates multiple agents, the next chapter is essential.

Chapter 18Multi-Agent Evaluation

First Principle
When multiple specialists collaborate, two new problems emerge that don't exist with a single agent. First: who do you blame when the output is bad? The researcher, the writer, or the coordinator who managed them? Second: who evaluates the coordinator? The coordinator's job is to decompose, delegate, and synthesize. If the final output is wrong, it could be because a sub-agent produced bad work, or because the coordinator assigned the wrong work to the wrong sub-agent, or because it failed to synthesize good sub-agent work into a coherent result. You need evaluation at every layer.

When Multi-Agent Eval Matters (and When It Doesn't)

Before investing in multi-agent evaluation, check whether it applies to your product.

You need multi-agent evaluation if:

  • Your product uses an orchestrator that delegates to specialized sub-agents (e.g., a "lead researcher" coordinating "search agents")
  • Your product runs agents in parallel that need to be synthesized (e.g., multiple research agents investigating different aspects of a topic)
  • Your product uses a generator-evaluator pair (one agent creates, another critiques)
  • Your product has routing logic that sends different tasks to different specialized agents

You do NOT need multi-agent evaluation if:

  • Your product uses one agent that calls multiple tools (that's single-agent, covered in Chapters 15-17)
  • Your "multi-agent" system is really just sequential prompt chaining (covered in Chapter 15 as step-level eval)
  • Your agents never interact with each other — they handle completely separate user requests

If you have one agent, skip this chapter. Come back when your architecture evolves. The rest of Phase 5 — step-level, tool use, and memory evaluation — covers everything you need for single-agent products.

The 4-Layer Evaluation Architecture

Based on synthesis across Anthropic, Braintrust, and DeepEval's research, multi-agent systems need evaluation at four distinct layers. Each layer answers a different question and requires a different evaluation approach.

Why You Need All 4 Layers

Each layer catches failures that the other layers miss:

  • Layer 1 catches component failures: The research agent is hallucinating. The writer agent is ignoring brand voice. You'd never know from the end-to-end score alone, because the orchestrator might partially compensate for a bad sub-agent.
  • Layer 2 catches coordination failures: Every sub-agent is excellent, but the orchestrator assigned the research task to the writing agent and the writing task to the research agent. Individual agents pass. End-to-end fails. Layer 2 diagnosis: bad routing.
  • Layer 3 catches integration failures: All sub-agents are great. The orchestrator routes correctly. But the synthesis step — combining three sub-agent outputs into one coherent deliverable — loses critical information or introduces contradictions. Only end-to-end evaluation catches this.
  • Layer 4 catches efficiency failures: Quality is perfect. But the system used 3 million tokens and took 12 minutes for a task that should cost $0.50 and take 30 seconds. Without efficiency evaluation, you're shipping a product that works but is economically unsustainable.

The Key Finding

Multi-Agent Performance
The multi-agent system outperformed single-agent Claude Opus 4 by 90.2% on their internal research eval. For breadth-first queries requiring multiple independent research directions, multi-agent approaches excelled.

What Humans Caught That Automation Missed

Even with a sophisticated LLM judge, Anthropic found that human review caught three categories of failure that automation missed:

  1. Hallucinations — The LLM judge sometimes couldn't verify whether a specific claim was true without access to the original sources. Humans could cross-reference.
  2. System failures — Edge cases where the agent architecture itself broke (timeouts, lost sub-agent responses, synthesis errors) that the LLM judge interpreted as low-quality output rather than infrastructure failure.
  3. Subtle source selection biases — Sub-agents preferred SEO-optimized content over authoritative academic PDFs. The LLM judge rated the content quality without noticing that the source selection was systematically biased toward popular but less authoritative sources.

This last finding is particularly important. It's a Layer 1 failure (sub-agent behavior) that manifests as a subtle Layer 3 quality degradation. Without human review specifically looking for source quality patterns, it would go undetected indefinitely.

Efficiency Evaluation: The Hidden Layer

Layer 4 — efficiency — is the layer most teams add last and wish they'd added first. Quality is necessary but not sufficient for a sustainable product. An agent that produces perfect output but costs $5 per request and takes 3 minutes to respond is not a viable product, no matter how good the results are.

Efficiency evaluation tracks four metrics:

MetricWhat to TrackRed Flag ThresholdHow to Improve
Token Cost Total input + output tokens across all agents per request Varies by product, but if cost-per-request exceeds revenue-per-request, you have an economics problem Reduce sub-agent verbosity, use smaller models for simpler sub-tasks, cache common queries
Wall-Clock Time Total time from user request to final response Depends on task complexity. Research tasks: 30-120s acceptable. Chat responses: >5s feels slow Parallelize independent sub-agents, reduce sequential dependencies, use faster models where quality allows
Agent Invocations Number of sub-agent calls per request If invocations grow over time without quality improvement, the orchestrator is being wasteful Review orchestrator logic for unnecessary decomposition, merge sub-agents with overlapping responsibilities
Parallelization Effectiveness Ratio of total sequential time to actual wall-clock time If 4 sub-agents run sequentially when they could run in parallel, you're paying a 4x latency penalty for no reason Identify independent sub-tasks and dispatch them concurrently

A simple efficiency scorecard for each request: total tokens used, total cost in dollars, wall-clock time, and number of agent invocations. Track these over time. Set baselines from your first 100 requests. Flag any request that exceeds 2x the baseline. Investigate why.

Efficiency in Practice
A multi-agent research system processes a query. The orchestrator spawns 4 research sub-agents. Each sub-agent runs 3 search queries and reads 5 pages. That's 12 search calls and 20 page reads. Total: ~500K tokens, $1.20, 90 seconds.

Investigation reveals: 3 of the 4 sub-agents researched overlapping topics. 8 of the 20 pages were irrelevant. The orchestrator could have identified the overlap and spawned 2 sub-agents instead of 4, cutting tokens by 40% and time by 30%.

This is a Layer 2 (orchestration) problem with Layer 4 (efficiency) consequences. Without efficiency tracking, you'd never notice — the output quality was fine. The cost was just unnecessarily high.

DeepEval's Counting Rule

A practical detail that matters for metrics: how do you count "turns" in a multi-agent system?

The Counting Rule
Only count end-to-end user-facing interactions as turns. Agent-to-agent calls are component-level interactions, not turns.

Why this matters: If your orchestrator sends 5 messages to sub-agents and each sub-agent responds 3 times, that's 20 internal messages. But from the user's perspective, they sent 1 message and got 1 response. That's 1 turn, not 21. If you count internal messages as turns, your "multi-turn accuracy" metric will be measuring something entirely different from the user's experience.

Track internal agent interactions at Layer 1 and Layer 2 (for debugging and optimization). Track user-facing turns at Layer 3 (for quality metrics). Never conflate the two.

The Evaluator-Optimizer Pattern

One of the most powerful multi-agent patterns doesn't just USE evaluation — it builds evaluation INTO the agent architecture itself.

Anthropic describes a three-agent architecture from their work on long-running coding agents:

  1. Planner agent — creates the plan for the task
  2. Generator agent — produces the output (code, text, whatever)
  3. Evaluator agent — provides critical feedback on the generator's output

The evaluator agent IS the eval mechanism. It's not external infrastructure running after the fact — it's an active participant in the generation process. The generator produces output, the evaluator critiques it, the generator revises based on the critique, the evaluator checks again. This loop continues until the evaluator is satisfied or a budget limit is reached.

This pattern produced "rich full-stack applications over multi-hour autonomous coding sessions" because the system had a built-in quality check that caught errors during generation, not after.

Architectural Evaluation vs. External Evaluation
The Evaluator-Optimizer pattern blurs the line between "building the agent" and "evaluating the agent." The evaluator agent serves both purposes: it improves the output during generation AND it provides evaluation data for your quality metrics. This is elegant but creates a risk: if the evaluator agent has blind spots, those blind spots exist in both the generation quality and the eval data. You still need external evaluation to catch what the internal evaluator misses. The Evaluator-Optimizer handles the "make it better in real-time" job. Your eval suite handles the "is it actually getting better over time?" job.

When to Use Multi-Agent Eval vs. Just End-to-End

Multi-agent evaluation is more complex and more expensive than end-to-end evaluation. Don't add it until you need it. Here is the decision framework:

Quality is generally good End-to-end evaluation only If the system works, don't add complexity to diagnose problems that don't exist yet
End-to-end scores are low but you can't diagnose why Add Layer 1 (individual agent eval) Test each sub-agent independently. Find which one is underperforming. Fix it.
Individual agents are good but combined output is bad Add Layer 2 (orchestration eval) The agents are fine. The coordination is broken. Evaluate decomposition, routing, and synthesis.
Quality is fine but cost/latency is too high Add Layer 4 (efficiency eval) Track tokens, time, and invocation count. Identify redundant agent calls, unnecessary parallelization, or overly verbose sub-agents.
All of the above Full 4-layer evaluation You have a complex system with multiple failure surfaces. Invest in full visibility.
The Sequence That Saves Time
Always start with Layer 3 (end-to-end). If end-to-end quality is high, you're done — ship it and monitor. If end-to-end quality is low, add Layer 1 to find the weak agent. If all agents are individually good, add Layer 2 to check coordination. Add Layer 4 only when quality is acceptable but economics aren't.

This sequence ensures you never build evaluation infrastructure for a problem that doesn't exist.

What Changes As Models Improve

One important caveat: the 90.2% improvement that Anthropic saw from their multi-agent system over a single agent is a measurement of current-generation models. As models become more capable, the gap between single-agent and multi-agent approaches may narrow. If a single Claude Opus 5 can match the quality of an Opus 4 + three Sonnet 4 sub-agents, the evaluation problem simplifies dramatically — you go back to single-agent evaluation from Chapters 15-17.

The multi-agent evaluation architecture you build today should be designed to be dismantled if the agents themselves become unnecessary. Don't over-invest in multi-agent evaluation infrastructure that becomes irrelevant when the next model generation ships. Build it modular. Each layer should be independently removable.

The 7 Most Common Mistakes in Agent-Specific Evaluation

Before we close Phase 5, here are the mistakes we see teams make most often when evaluating agent-specific behaviors. Every one of these has cost real teams real weeks of wasted effort.

#MistakeWhy It HappensThe Fix
1 Evaluating only the final output It's easiest. It's how chatbots were evaluated. Step-level eval requires more infrastructure. Add at least 2-3 eval gates at transformation boundaries. Even lightweight deterministic gates catch cascading failures.
2 Checking the agent's response text instead of the tool call log The response is user-visible. The log is hidden. PMs naturally focus on what users see. For any task that requires tool execution, always verify against the actual tool call trace. Ghost Actions are invisible in the response text.
3 Testing memory with short conversations only Short tests run faster and are easier to write. 5-turn tests feel sufficient. You MUST test at 20+ turns. Context rot, persistence failures, and constraint accumulation only surface in long conversations.
4 Rigid trajectory matching It feels precise. It's deterministic. It's easy to automate. Use outcome-based evaluation by default. Agents should be free to find creative solutions. Only use strict trajectory matching for compliance-driven workflows.
5 Testing happy paths only for tool use It's natural to test that the agent does the right thing when everything works. It's less natural to test what happens when tools fail. Build explicit tests for tool failures: empty results, error responses, rate limits, wrong-entity returns. The Confident Fabricator only shows up when tools return bad data.
6 Skipping environment reset between eval runs It's slow. It requires Docker or similar infrastructure. It seems unnecessary when tests are "independent." Agent tests are never truly independent. File creation, database changes, and cached results leak between tests. Invest in resettable environments early.
7 Over-investing in multi-agent eval before validating end-to-end Multi-agent architectures are complex, and complex systems feel like they need complex evaluation. Start with Layer 3 (end-to-end). Only add Layers 1, 2, and 4 when end-to-end results show problems you can't diagnose.

If you avoid these seven mistakes, you'll be ahead of 90% of teams building agent evaluation systems. Most of the wasted time in agent eval comes not from missing techniques but from applying the wrong technique at the wrong time, or from evaluating the wrong surface entirely.
