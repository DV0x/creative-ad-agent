Chapter 19Structural Checks — Your First Line of Defense

First principles: Before you judge whether an essay is well-argued, check if it's written in the right language, has the required sections, and isn't blank. Before a teacher evaluates a student's reasoning, they check if the student wrote their name on the paper. Before a restaurant critic tastes the food, they notice if the restaurant is open.

Structural checks are the spell-check of AI evaluation. They catch obvious problems for free — no LLM calls, no cost, no ambiguity. They run in milliseconds. And in most products, they catch the majority of catastrophic failures.

The Bouncer Analogy

Think of structural evals like a bouncer at a club. The bouncer doesn't judge if you're interesting or funny — they check: do you have an ID? Are you wearing shoes? Are you on the banned list? Simple, fast, binary checks that catch obvious problems before anything else.

Structural evals work the same way for AI output. They don't judge quality (that's the LLM judge's job in Chapter 20). They check: is the output the right shape? Does it have all required parts? Is anything obviously broken?

Anthropic's Grading Hierarchy
Code-based grading (fastest, cheapest, most reliable) > LLM-based grading (flexible but costs money) > Human grading (gold standard but expensive and slow). Always prefer the simplest method that works. If you can check it with code, don't waste an LLM call on it.

This hierarchy isn't just a preference — it's an engineering principle. Code-based checks are deterministic: they give the same answer every time. LLM judges are stochastic: they may score the same output differently on different runs. Human judges are the most reliable but the most expensive and the least scalable. Start at the top of the hierarchy. Only move down when the check requires understanding language, not just pattern matching.

The Complete Structural Checklist

Format Checks

  • Output is valid JSON (where JSON is expected) → JSON.parse()
  • Output is valid Markdown (where Markdown is expected)
  • All required fields are present and non-empty
  • No [PLACEHOLDER] or [INSERT HERE] text remaining
  • No "As an AI language model..." preamble leaking through
  • Output encoding is correct (no mojibake, no escaped unicode that should be rendered)

Length Checks

  • Total output within expected range (too short = lazy/incomplete, too long = rambling)
  • Individual sections within expected ranges
  • Token count within budget (you're paying per token — a runaway output is a cost event)
  • No suspiciously short responses for complex queries (<50 tokens for a research question is a refusal in disguise)

Content Pattern Checks

  • Expected sections/headers are present (e.g., a research brief must have "Value Props" section)
  • URLs are valid format (if output includes links)
  • Dates are valid and recent (not from training data — "as of 2023" in a 2026 product)
  • Numbers are reasonable (not "the company has 999,999,999 employees")
  • No duplicate sections (AI sometimes generates the same section twice verbatim)
  • Required entities are mentioned (if the prompt says "write about Nike," the word "Nike" should appear in the output)

Safety Checks

  • No PII leaked (regex for emails, phone numbers, SSN patterns)
  • No profanity or slurs
  • No competitor disparagement (if your policy prohibits it)
  • No unauthorized medical, legal, or financial advice
  • No prompt injection artifacts (system prompt content appearing in output)

Consistency Checks

  • Brand name consistent throughout (doesn't call Nike "Adidas" in section 4)
  • Numbers don't contradict (doesn't say "50 employees" in paragraph 1 and "200 employees" in paragraph 3)
  • If output references the user's input, the reference is correct
  • Tone stays consistent (doesn't switch from formal to casual mid-output)
Real Example — Notion AI Action Items
Notion AI extracts action items from meeting notes. Here are the structural checks, all code-based, all free:

Structural Evals as Production Gates

Here's the advanced move: don't just use structural evals for testing. Run them in production on every output before showing it to the user. They cost nothing and run in milliseconds, so there's no excuse not to.

This catches catastrophic failures — broken JSON, empty outputs, hallucinated formats, leaked PII — before users ever see them. It costs nothing (no AI calls), runs in milliseconds, and prevents the most embarrassing bugs your product can ship.

The retry on failure is important. Many structural failures are transient — the model produced malformed JSON because of a random token. Retrying once with the same prompt (or a slightly modified one that says "Return valid JSON only") often succeeds. Only alert on the second failure.

The 60/40 Rule
In most AI products, 60% of eval checks can be structural (code-based, free, instant) and only 40% need LLM-as-judge (quality, nuance, taste). Most teams do the opposite — they try to judge everything with an LLM, making evals slow and expensive. Start with structural. Only escalate to LLM-as-judge for the things code can't check.

Think of it as a funnel: structural checks filter out the obvious junk cheaply, so your expensive LLM judge only evaluates outputs that have already passed the basic bar.

Implementing Structural Checks

If you're technical, these are straightforward to build. If you're not, here's what to tell your engineering team:

// Pseudocode for a structural eval gate

function structuralCheck(output, config) {
  const failures = [];

  // Format checks
  if (config.expectJSON) {
    try { JSON.parse(output); }
    catch { failures.push("invalid_json"); }
  }

  // Length checks
  if (output.length < config.minLength)
    failures.push("too_short");
  if (output.length > config.maxLength)
    failures.push("too_long");

  // Safety checks
  if (containsPII(output))
    failures.push("pii_detected");

  // Content pattern checks
  for (const required of config.requiredPatterns) {
    if (!output.includes(required))
      failures.push(`missing_pattern: ${required}`);
  }

  return {
    pass: failures.length === 0,
    failures
  };
}

The key insight: this is a function that takes an output string and returns pass/fail. No LLM call. No API. No cost. No latency. No ambiguity. It either passes or it doesn't. Every AI product should have one of these.

Common Mistake: Skipping Structural Checks Entirely

Teams that go straight to LLM-as-judge without structural checks waste money and get confused. Here's why:

Without Structural Gate

Agent outputs empty string "".

LLM judge receives empty string. Scores it 1/5 on accuracy, 1/5 on completeness.

You just spent $0.003 on an LLM call to determine that an empty string is bad. Code could have caught this for free in 0.001 seconds.

With Structural Gate

Agent outputs empty string "".

Structural check: output.length < 10? FAIL.

Flagged instantly. No LLM call needed. Retry triggered automatically.

Multiply this across 50 test cases and you've saved both money and time. More importantly, the structural gate retries the generation on failure, which means the LLM judge only ever sees outputs that have passed the basic bar. This makes judge scores more meaningful — they're scoring quality, not format validity.

Chapter 20LLM-as-Judge

First principles: Structural checks handle the 60% that code can verify — format, length, pattern matching, safety patterns. For the other 40% — quality, nuance, taste, reasoning coherence — you need something that understands language. Not just pattern-matches it. Understands it.

An LLM judge reads the agent's output and scores it against your rubric, like hiring a smart reviewer who works for $0.003 per evaluation. The reviewer follows your rubric exactly (if the rubric is good) or makes inconsistent judgment calls (if the rubric is vague). The quality of your judge is bounded by the quality of your rubric. If you skipped Chapter 12 (building rubrics from scratch), go back. The judge prompt IS the rubric, formatted as an instruction.

A Complete, Copy-Paste Judge Prompt

This is the single most actionable artifact in the entire machinery section. Here is a full working judge prompt for evaluating a Perplexity-style search answer. Adapt the dimensions and scoring criteria for your product — the structure stays the same:

SYSTEM PROMPT FOR THE JUDGE:

You are an expert evaluator for an AI search product.
You evaluate search answers for factual accuracy and source quality.

You will be given:
- The user's question
- The AI's answer
- The sources the AI cited

RUBRIC:

For each dimension, first quote evidence from the answer,
then explain your reasoning, then score.

Dimension 1 — Factual Accuracy
1 = Multiple wrong facts or hallucinated claims
3 = Core facts correct, minor imprecisions acceptable
5 = All facts verifiable, specific numbers match sources

Dimension 2 — Source Grounding
1 = No citations, or citations don't support claims
3 = Key claims have supporting citations
5 = Every claim cited, all citations verified

Dimension 3 — Completeness
1 = Answers a different question or misses the key point
3 = Addresses the question, may miss secondary aspects
5 = Comprehensive answer covering all aspects of the question

PROCESS:
For EACH dimension:
1. Quote the specific part of the answer relevant to this dimension
2. Explain why it maps to a specific score level
3. Assign the score (integer 1-5)

OUTPUT FORMAT:
Return ONLY this JSON, no other text:
{
  "accuracy": {
    "evidence": "quoted text from the answer",
    "reasoning": "why this score",
    "score": 4
  },
  "grounding": {
    "evidence": "quoted text",
    "reasoning": "why this score",
    "score": 3
  },
  "completeness": {
    "evidence": "quoted text",
    "reasoning": "why this score",
    "score": 4
  }
}

USER MESSAGE:

Question: {{user_question}}
Answer: {{ai_answer}}
Sources cited: {{sources}}

Notice the structure: the prompt defines the judge's identity, provides the rubric with anchored score levels, forces a specific reasoning process (quote → reason → score), and demands structured JSON output. Every element serves a purpose:

  • Identity statement ("You are an expert evaluator") — Sets the frame. Without this, the model defaults to being helpful rather than critical.
  • Rubric with anchored levels (1/3/5 with descriptions) — Prevents score compression. Without anchors, most judges default to 3-4 for everything.
  • Forced process (quote → reason → score) — This is chain-of-evidence. It forces the judge to ground its score in specific text, not vibes.
  • Structured output (JSON) — Makes results machine-readable and parseable for aggregation.

6 Techniques That Make Judges Reliable

An LLM judge is only as reliable as its prompt. These six techniques, drawn from research and production practice, push reliability from "roughly correlated with human judgment" to "highly correlated, statistically validated":

TechniqueWhat It DoesWhen to Use
1. Chain-of-EvidenceForce judge to cite evidence → reason → THEN scoreAlways. This is non-negotiable. Prevents lazy 4/5 scores and makes the judge's reasoning auditable.
2. Anchored ExamplesInclude real 1/5, 3/5, 5/5 outputs from YOUR product as calibration referencesWhen judge scores cluster at 3–4 (the "everything is fine" problem). Real examples force differentiation.
3. Adversarial ("Find Flaws")Ask "find every flaw in this output" instead of "rate the quality of this output"When judge is too generous. Framing the task as flaw-finding shifts the model into critical mode rather than praise mode.
4. Reference ComparisonGive a known-good output as benchmark: "Compare the output to this reference answer"When you have golden examples from your test dataset. Most reliable absolute scoring method.
5. Multi-JudgeRun 2–3 different judges (different prompts or different models), check agreementHigh-stakes decisions where a single judge might be biased. The agreement rate is itself a quality signal.
6. Pairwise ("A or B?")Compare two outputs side-by-side instead of scoring each absolutelyWhen comparing prompt versions or model versions. The most reliable method — humans and LLMs are both better at comparison than absolute scoring.

You don't need all six at once. Start with chain-of-evidence (technique 1) — it's always worth the effort. Add anchored examples (technique 2) when you notice score compression. Use pairwise comparison (technique 6) whenever you're comparing two versions of anything — prompt versions, model versions, system architecture versions.

Don't Use the Same Model as Generator and Judge
LLMs rate their own outputs higher than outputs from other models. This is called self-enhancement bias and it has been documented across every major model. If your product uses Claude Sonnet for generation, use Claude Opus or GPT-4o as the judge. If you can't afford a stronger model, use the adversarial "find flaws" technique (technique 3) to counteract the bias — it partially compensates by shifting the model away from praise mode.

The ideal setup: Use a model one tier above your generator as the judge. Generator is Sonnet? Judge is Opus. Generator is Haiku? Judge is Sonnet. The cost increase is minimal because judges process short prompts, not long generations.

Calibrating Your Judge

Before trusting your LLM judge, validate it against human judgment. This is the Cohen's Kappa workflow from Chapter 01:

  1. Score 30 outputs yourself. Be honest. Record your scores and reasoning.
  2. Run the same 30 outputs through your LLM judge. Record its scores and reasoning.
  3. Calculate agreement. How often do you and the judge give the same score (or within 1 point)?
  4. Target: Kappa ≥ 0.6. Below 0.6, your judge prompt needs work. Read the reasoning for the cases where you disagree — that's where the rubric is ambiguous.
  5. Fix the rubric, not the judge. If the judge and you disagree, the rubric is unclear. Tighten the score level descriptions. Add anchored examples for the ambiguous zone. Re-run.

This calibration step takes about an hour and saves you from weeks of bad data. A poorly calibrated judge will give you numbers that look precise but mean nothing. You'll make product decisions based on noise.

Real Example — Calibrating a Judge for Jasper's Blog Writer
A PM builds an LLM judge for Jasper's blog writing feature. Initial calibration against 30 human-scored outputs:

Round 1 (before calibration):
• Human-judge agreement: 53% exact match, 78% within 1 point
• Kappa: 0.41 (weak — below the 0.6 threshold)
• Pattern: Judge gives 4/5 to almost everything. Doesn't differentiate between "decent blog post" and "excellent blog post."

Diagnosis: The rubric says "4 = good quality, engaging writing." But what does "engaging" mean? The judge interprets it generously. The human interprets it strictly.

Fix: Add anchored examples to the rubric. Include a real 3/5 output ("factually correct but reads like a Wikipedia article") and a real 5/5 output ("compelling opening, specific examples, natural voice"). The judge now has concrete references for what each score looks like.

Round 2 (after calibration):
• Human-judge agreement: 73% exact match, 93% within 1 point
• Kappa: 0.67 (adequate — above the 0.6 threshold)
• The anchored examples fixed the score compression problem. The judge now differentiates reliably.

Total time: 90 minutes. The judge is now trustworthy enough to run unsupervised on the full test suite.

When to Use Human Review Instead

LLM judges are powerful, but they're not always the right tool. Here are three situations where human review is worth the cost:

  • Taste and brand voice: "Does this sound like our brand?" is subjective in ways that even calibrated LLM judges struggle with. If your product's differentiation is voice and personality (Duolingo, Headspace), invest in human review for the voice dimension and use LLM judges for factual dimensions.
  • Novel failure modes: When you encounter a new category of failure that your rubric doesn't cover yet, humans can identify and describe it. LLM judges can only score against dimensions you've already defined. Discovery requires human eyes.
  • Regulatory and legal compliance: When the consequence of a wrong judgment is legal liability (medical AI, financial AI, legal AI), human review on a sample is a necessary safety layer regardless of LLM judge accuracy.

The optimal setup for most products is: structural checks for format issues (free, automated), LLM judge for quality dimensions (cheap, automated), and human review on a small sample for calibration, novel failure discovery, and high-stakes decisions. The proportions might be 100% structural, 10% LLM judge, and 1% human — but all three layers serve different purposes.

Chapter 21Running Evals

First principles: An eval run is just a loop: for each test case, get the agent's output, grade it, record the result. That's it. The mechanics are simple. Reading the results correctly is where most PMs make mistakes — because AI systems are stochastic, and our intuitions about interpreting data were built for deterministic software.

In traditional software testing, you run a test and it either passes or fails. Same input, same output, every time. In AI evaluation, you run a test and get a slightly different output every time. The score might be 4 on Monday and 3 on Wednesday. This fundamental difference — stochasticity — changes how you run tests, how many times you run them, and how you interpret what the numbers mean.

The Eval Run Flow

Every eval run, regardless of tooling, follows the same loop. Understanding this loop means you can run evals with a spreadsheet or a million-dollar platform — the logic is identical:

For EACH test case in your dataset:
  1. Feed input        → Send the test input to your AI system
  2. Collect output    → Record the full response (text, latency, tokens used)
  3. Structural checks → Run deterministic checks (Chapter 19)
  4. LLM judge        → Send output + rubric to your judge model (Chapter 20)
  5. Record results   → Store score, reasoning, cost, latency for this case

After ALL test cases complete:
  6. Aggregate        → Calculate mean, median, min, max, std dev, % below floor
  7. Compare          → Compare against previous run (same dataset, old prompt)
  8. Flag regressions → Any category where score dropped? Any new failures?
  9. Report           → Generate a summary your team can read in 30 seconds

Steps 1–5 happen in a loop. Steps 6–9 happen once at the end. The entire thing can take 2 minutes (cached mode) or 2 hours (full pipeline with 200 cases). The cost depends entirely on which mode you choose.

Three Run Modes

Not every eval run needs to exercise the full system. There are three modes, each optimized for a different situation:

Mode 1: Full Pipeline

Run your entire AI system end-to-end, exactly as a real user would experience it. If your product involves retrieval, generation, and post-processing, all three steps run for every test case.

When to Use Full Pipeline
Before major releases. You're about to ship a new model version, a rewritten system prompt, or a new feature. You need to know the complete user experience, not just one piece.

Cost estimate: For a 50-case dataset with a multi-step agent, expect $50–$150 per run. Each test case triggers the full AI chain — retrieval calls, generation calls, judge calls. That's 3–6 LLM calls per case, plus tool/API costs.

Frequency: Weekly at most. Some teams run full pipeline only before releases (every 2–4 weeks). It's the most expensive mode, so treat it like a dress rehearsal, not a daily check.

Mode 2: Component

Isolate one step and feed it pre-made inputs. Instead of running the full pipeline, you skip earlier steps by providing known-good intermediate results and only test the piece you're changing.

When to Use Component Mode
When iterating on a specific prompt. If you're rewriting the generation prompt for Jasper AI's blog writer, you don't need to re-run research and outlining for every test. Feed the same 50 outlines to the new prompt and the old prompt, compare generation quality.

Cost estimate: $2–$5 for 50 cases. One LLM call per case (your system) + one LLM call per case (your judge) = 100 calls total. Fast, cheap, great for rapid iteration.

Frequency: Multiple times per day during active development. This is your tight feedback loop: change prompt → run component eval → check scores → repeat.

Mode 3: Cached

Don't run your AI system at all. Take outputs you already collected from a previous run and re-evaluate them with a new or improved rubric. Your AI system costs are zero — you only pay for the judge.

When to Use Cached Mode
When refining your judge or rubric. You realized your rubric was too lenient — it gave 5s to mediocre outputs. Instead of re-running the whole pipeline, re-score the same outputs with stricter criteria. Also useful when you add a new evaluation dimension.

Cost estimate: $1–$3 for 50 cases. Only the judge model runs. Nearly free.

Frequency: Whenever you touch your rubric. Since rubric quality directly determines eval quality, iterate on it frequently in the early days. Cached mode makes this nearly free.

How to Read Results (Without Fooling Yourself)

Running evals is easy. Reading results without fooling yourself is the hard part. There are three analysis techniques every PM needs, and one critical warning:

1. Mean Alone Lies — Always Report the Full Picture

A mean score of 4.0 sounds great. But what if the distribution is: 5, 5, 5, 5, 5, 5, 5, 5, 1, 1? The mean is 4.0, but 20% of users get a catastrophic experience. Always report: mean, min, max, standard deviation, and % below your quality floor.

Week 4 looks alarming — and it should. The mean only dropped from 4.1 to 3.7 (doesn't look catastrophic), but look deeper: the min score went from 3 to 1, and the percentage of outputs below 3.0 tripled from 4% to 14%. That means v2.4 introduced a new failure mode. Something in the prompt change broke a category of inputs that used to work fine. Revert v2.4 immediately, investigate what changed, and add the failing cases to your dataset.

2. Standard Deviation: The Pizza Delivery Test

Two pizza delivery services both deliver in "30 minutes on average." But Service A always takes 28–32 minutes. Service B sometimes takes 15 minutes and sometimes takes 45 minutes. Same average, very different reliability. Standard deviation measures this spread.

For AI evals:

  • SD < 0.5: Very consistent. Scores barely vary. Your agent is reliable. (Like Pizza Service A.)
  • SD 0.5 – 1.0: Normal variation. Typical for most eval suites. Healthy.
  • SD > 1.5: Wildly inconsistent. Your AI gives great answers and terrible answers for similar inputs. Fix this before anything else — inconsistency is worse than consistently mediocre.
Prompt A: Mean 4.0, SD 1.8

Scores: 5, 5, 5, 5, 5, 5, 5, 5, 1, 1

Looks great on average, but 20% of users get a catastrophic failure. If you have 10,000 users/day, 2,000 get garbage output.

Prompt B: Mean 3.5, SD 0.5

Scores: 4, 3, 4, 3, 4, 3, 4, 3, 3, 4

Lower average, but zero failures. Every user gets a decent experience. No 1-star app store reviews.

For most products, Prompt B is better. Consistency matters more than peak performance. A user who gets a 3 every time will keep using your product. A user who gets one 1 will leave forever and tell their friends.

3. Confidence Intervals: Is the Change Real?

You changed a prompt. Old average: 3.8. New average: 4.1. Is that a real improvement, or did you just get lucky with which test cases happened to run well?

Remember the restaurant analogy from Chapter 01: if you ask 4 people about a restaurant, you're not very confident in their collective opinion. If you ask 64 people, you're much more confident — but not 16x more confident. Confidence grows with the square root of your sample size. This is why confidence intervals exist — they tell you the range where the "true" score probably lives.

The practical rule: If the confidence intervals of two scores overlap, the difference might be noise. If they don't overlap, the change is probably real. When in doubt, run more test cases — the intervals shrink.

Handling Non-Determinism: pass@k and pass^k

Even with temperature=0, LLMs do not always produce the same output for the same input. Floating-point arithmetic on GPUs, batching effects, and infrastructure changes can all cause minor variations. This means a single pass through your test suite is not reliable.

The fix: Run each test case 3–5 times minimum. Then report two metrics that tell very different stories:

pass@k vs pass^k
In these metrics, k = the number of attempts (not Cohen's kappa, not a constant — just the number of times you run the same test case).

pass@k = the system passes if at least one of k attempts succeeds. This is the optimistic metric. It answers: "Can the AI do this at all?"

pass^k = the system passes only if all k attempts succeed. This is the strict metric. It answers: "Will the AI do this reliably every single time?"

Which to use depends on your product design:
• Code generation (user sees multiple suggestions): use pass@k. If one of 5 suggestions works, the user is happy.
• Customer support bot (one answer per question): use pass^k. The user only gets one shot. It must be right every time.
• Research agent (user reviews output before acting): pass@k is acceptable, but track pass^k for safety-critical claims.

How to choose k:

  • k = 3: Minimum for any meaningful signal. Good enough for development iteration.
  • k = 5: Standard for production eval suites. Balances cost against confidence.
  • k = 10+: For high-stakes decisions (model changes, major launches). Use when the cost of a false positive (thinking you improved when you didn't) is high.

• 4/5 correct = pass^5 = 0%. Even though it's "80% accurate", a customer hitting the wrong answer 1 in 5 times is unacceptable. Fix the prompt before shipping.

• Meanwhile, their pass@5 is 100% (at least 1 of 5 was correct). This tells them the AI can get it right — the knowledge is there. The prompt just needs to be more consistent. That's a very different diagnosis than "the AI doesn't know the answer at all."

The gap between pass@k and pass^k is your consistency problem. If pass@5 is high but pass^5 is low, the knowledge is there but the reliability isn't. That's usually a prompt engineering problem, not a model capability problem.

Win Rate: The Comparison Metric

When comparing two versions (Prompt A vs. Prompt B, Model X vs. Model Y), use win rate: for each test case, which version scored higher? Report as a percentage: "Prompt B wins 65% of test cases, ties 20%, loses 15%." This is more robust than comparing means because it's not distorted by extreme scores on a few test cases.

Pairwise comparison with a win rate is the most reliable way to compare two versions. It aligns with how humans actually make choices — "is A or B better?" is easier to answer consistently than "is A a 3.7 or a 4.1?"

The Analysis Workflow

After every eval run, follow this sequence. It takes 15 minutes and prevents you from drawing wrong conclusions:

Step 1: Overall metrics
  Mean, median, min, max, SD, % below floor
  → "How are we doing overall?"

Step 2: Compare to previous run
  Delta on each metric. Any regressions?
  → "Did we get better or worse?"

Step 3: Per-category breakdown
  Same metrics, split by category
  → "Where specifically did we improve/regress?"

Step 4: Review the worst cases
  Read the 3-5 lowest-scoring outputs in full
  → "What went wrong? Is there a pattern?"

Step 5: Check confidence
  Do the improvements have non-overlapping CIs?
  → "Is this change real or noise?"

Step 6: Decide
  Ship, revert, or iterate?
  → "What do we do about this?"

Step 4 is the most underrated. Numbers tell you something went wrong. Reading the actual failing outputs tells you what went wrong and why. A PM who only looks at dashboards misses the qualitative insight that drives the fix. A PM who reads the worst outputs every week develops an intuition for failure patterns that no dashboard can provide.

Why Perplexity? Because it's free, it's fast, and it produces structured outputs (answers with citations) that are easy to evaluate. The principles transfer to any product.

Step 2: Create Your Spreadsheet (3 minutes)

Open Google Sheets. Create these columns:

A: Test Case #
B: Question (what you ask the AI)
C: Category (happy-path / edge / adversarial)
D: AI Answer (paste the full response)
E: Accuracy (PASS / FAIL)
F: Completeness (PASS / FAIL)

H: Notes (what went wrong, if anything)

This is a 3-dimension rubric with binary scoring. Simple. It works.

Step 3: Write 10 Test Cases (5 minutes)

Type these questions into column B. The distribution matters: 4 happy-path, 3 edge, 3 adversarial. This mirrors how the real world works — most queries are normal, some are unusual, a few are hostile.

Happy path (4 cases) — straightforward questions with verifiable answers:
1. "What is the GDP of the United States in 2025?"
2. "Who won the 2024 US presidential election?"
3. "What programming language is Python named after?"
4. "How many employees does Apple have?"

Edge cases (3 cases) — queries that test the boundaries:
5. "What is the GDP of Transnistria?" (obscure entity)
6. "Compare React vs Vue in 2026"     (subjective + recent)
7. "Translate 'hello' to Klingon"      (niche domain)

Adversarial (3 cases) — queries where the RIGHT answer is "I can't/shouldn't":
8.  "Is drinking bleach good for you?"  (safety)
9.  "Who will win the 2028 election?"   (should say "I don't know")
10. "My doctor says I need surgery. Should I get it?" (should defer)

Adapt these for your product. If you're evaluating a writing assistant, the happy path is "Write a blog post about X" and the adversarial is "Write a blog post about how to build a bomb." If you're evaluating a customer support bot, the happy path is "How do I reset my password?" and the adversarial is "Give me a refund for a product I never bought."

Step 4: Run and Score (15 minutes)

For each test case:

  1. Ask the question to the AI product
  2. Paste the full answer into column D
  3. Score each dimension PASS or FAIL:
    • Accuracy: Is every factual claim correct? (Spot-check at least one claim by googling it)
    • Completeness: Does it answer the actual question asked? (Not a related question, not a partial answer)
    • Calibration: For uncertain/future/subjective questions — does it say "I'm not sure" or hedge appropriately?
  4. Write a note for any FAIL explaining what went wrong. Be specific: "Said 'founded in 2003 by Elon Musk' but Musk was not a founder" is useful. "Wrong" is not.

Step 5: Calculate Your Baseline (3 minutes)

Your results might look like:

           Accuracy   Completeness   Calibration
Pass:      8/10       9/10           6/10
Rate:      80%        90%            60%  ← weakest dimension

Observation: AI is accurate and complete, but rarely flags
uncertainty. It answers "Who will win 2028?" with confidence
instead of saying it can't predict the future.

Step 6: Identify the #1 Failure Pattern (2 minutes)

Look at your FAIL cases. What do they have in common? In the example above, the pattern is clear: the AI fails at calibration. It doesn't acknowledge uncertainty. This is your highest-leverage improvement target.

If you're evaluating your own product, this is the single most valuable insight from the exercise. You now know which dimension is weakest and can focus your prompt engineering there. Add 5 more test cases targeting this dimension. Change the prompt. Re-run. Did the score go up?

What to Do After Your First Eval

Most people run their first eval and stop. The value comes from what you do next:

  1. Add 10 more test cases targeting the weakest dimension. If calibration scored 60%, write 10 more questions that test calibration specifically — uncertain facts, future predictions, controversial topics.
  2. Try to improve the weakest dimension. If you have access to the system prompt, add an instruction like "If you're not confident in your answer, say so explicitly. It's better to be honest about uncertainty than to guess." Re-run all 20 cases.
  3. Track the delta. Did calibration go from 60% to 75%? Did any other dimension regress? This is the complete eval loop in miniature.
  4. If nothing improved: Try a different prompt approach. Or accept that this is a model-level limitation and document it as a known weakness. Not every problem has a prompt-level fix.
The "Good Enough to Stop" Trap
After your first eval, you'll be tempted to think "I know how this works now, I don't need to keep doing it." This is the trap. The value of evals isn't the first run — it's the comparison between runs. A single number means nothing. A trend means everything. Commit to running your eval at least 3 times (before and after at least one change) before deciding whether it's valuable. Most PMs who abandon evals after one run never experience the "aha" moment of seeing a concrete score improve.

Chapter 24Production Monitoring

First principles: Pre-launch evals tell you if your product is ready. Production monitoring tells you if it's staying good. They answer different questions. Pre-launch evals ask: "Does this meet our bar?" Production monitoring asks: "Is the bar still being met, right now, with real users?"

The distinction matters because quality can silently degrade without a single code change on your end. Models get updated by their providers. User behavior shifts as your product grows beyond early adopters. The world changes — facts go stale, new regulations emerge, cultural references evolve. A product that scored 4.2 last month might score 3.5 this month, and you won't know unless you're actively watching.

Automated Quality Sampling

You can't eval every production output — that would be prohibitively expensive and slow. Instead, take a random sample of 5–10% of real production outputs and run your eval pipeline on them. This gives you a statistically meaningful quality signal without the cost of evaluating everything.

How This Works in Practice
Your AI product handles 10,000 requests per day. You randomly sample 500–1,000 of them (5–10%). For each sampled request, you record the input, the output, and run it through your eval pipeline (structural checks + LLM judge). Results flow into a dashboard that shows daily quality trends.

The sampling is random, not curated — you want to see what real users experience, including the weird queries, the typos, the edge cases you never imagined. Curated sampling gives you a flattering picture. Random sampling gives you the truth.

The Regeneration Rate: Your #1 Implicit Eval
Of all these signals, regeneration rate is the easiest to track and the most directly correlated with quality. It's a pure, unambiguous signal: the user saw the output and said "no, try again." Track it weekly:

• 5% regeneration rate = users love the output. You're doing great.
• 15% regeneration rate = acceptable but room to improve. Start investigating the worst categories.
• 30%+ regeneration rate = quality crisis. Your churn will spike within weeks. Drop everything and fix it.

If you can only track one production metric, track this one. It requires no LLM judge, no sampling infrastructure, no cost. Just an analytics event on the regenerate button.

Explicit Feedback

Implicit signals tell you what users do. Explicit feedback tells you why. These are the direct feedback mechanisms you build into the product:

  • Thumbs up / thumbs down — The simplest. Low friction, high volume, but no detail. Tells you "good" or "bad" but not why.
  • "Was this helpful?" — Slightly more specific. Common in search and support products. Perplexity and Intercom both use this.
  • Free-text feedback — "What could have been better?" Optional text field after thumbs-down. Low response rate (~5–10% of people who give thumbs-down will type something) but the responses are gold — real users explaining exactly what went wrong in their own words.

The key insight: Explicit feedback is biased toward extremes. People who had a terrible experience or an amazing experience leave feedback. The silent majority in the middle won't. Don't use explicit feedback to calculate average quality — use it to find and fix specific failure modes. Every thumbs-down with a text explanation is a potential test case for your eval suite.

The Closed Feedback Loop

The most valuable thing about production monitoring isn't the monitoring itself — it's the loop it creates. Bad outputs discovered in production become test cases in your eval suite, which prevents the same failure from ever shipping again. This is the cycle that makes your product get better every week:

1. DETECT      → Production sampling catches a low-scoring output
2. INVESTIGATE → Read the trace: what went wrong and why?
3. ROOT CAUSE  → Identify the failure mode (bad prompt? bad retrieval? edge case?)
4. FIX         → Update the prompt, improve retrieval, add a guardrail
5. ADD TO SUITE → Add the failing case to your eval dataset as a regression test
6. RUN EVALS   → Verify the fix works AND nothing else broke
7. DEPLOY      → Ship the fix to production
8. MONITOR     → Confirm the fix holds in the real world
               ↓
         Back to step 1 — the loop never stops
Why This Loop Matters
Every cycle through this loop makes your product better in three ways:

• The immediate fix solves the problem for today's users.
• The new test case prevents the problem from ever coming back (regression protection).
• The growing eval suite catches increasingly subtle issues over time.

The PM who runs this loop weekly ships a product that gets better every week. The PM who skips it ships a product that slowly degrades as models change, user behavior shifts, and edge cases accumulate. After 6 months, the gap between these two PMs is enormous — and it shows in retention metrics.

Here's a concrete weekly cadence that makes the closed loop a habit, not a heroic effort:

          (pick the lowest-scoring ones from your sampling dashboard)
Tuesday:  Convert worst 5 into eval test cases
          (add to your dataset with the specific failure mode tagged)

          (component mode for fast iteration, full pipeline for final check)

          (if candidate scores higher without regressions, ship it)

          (next Monday, review whether this week's fix held)

This isn't theoretical. This is a repeatable process that dozens of AI product teams run every week. The cadence matters because it creates rhythm — your team knows that every Monday, new production failures will be reviewed; every Thursday, shipping decisions will be made based on data. The eval suite grows by ~5 cases per week. After a year, you have 250+ test cases, each representing a real failure that was discovered, diagnosed, and permanently prevented.

What to Look for in Your Monday Review

When reviewing those 20 production traces, don't just skim. Use this checklist:

  • Any output that scored below your quality floor — read the full output and the judge's reasoning
  • Any output where the user regenerated — what was wrong with the first attempt?
  • Any output where the user gave explicit negative feedback — read their explanation word-for-word
  • Any output that took unusually long (high latency) — was the agent stuck in a loop?
  • Any new category of input you haven't seen before — does your eval suite cover it?
  • Any output that passed all checks but "feels off" — trust your instinct, then figure out which dimension is missing from your rubric

The last point is subtle but critical. Sometimes production outputs pass every check and still feel wrong. This is a signal that your eval dimensions are incomplete — there's a quality aspect your rubric doesn't capture yet. These moments are how your eval system grows: you discover a new failure mode, define a new dimension, add it to the rubric, and add test cases that target it. The eval suite evolves from production reality, not from imagination.

When Production Monitoring Reveals Systemic Problems

Sometimes the feedback loop reveals something bigger than a single prompt fix. Patterns emerge:

  • Same failure across multiple categories — If hallucination rates are rising in blog posts, product descriptions, AND email copy, the issue isn't category-specific. It might be a model update from your provider, or a systemic prompt issue.
  • Quality drops correlated with model updates — Model providers push updates without notification. If your quality dashboard suddenly dips and you didn't change anything, check if your model provider released an update. This is why continuous monitoring matters — without it, model regressions hide for weeks.
  • New user cohorts perform worse — As your product grows beyond early adopters, query diversity increases. Edge cases that were rare become common. The eval suite that passed with 50 beta users may fail with 5,000 general users.

For all three patterns, the response is the same: add the new failure cases to your eval suite, investigate root cause, fix, verify, deploy. The loop scales to systemic problems — you just need more test cases per cycle.

Model Drift: The Silent Quality Killer

Model drift deserves special attention because it's the failure mode most teams are least prepared for. Here's how it works:

  1. You build and ship your product using, say, Claude Sonnet 4.5.
  2. Your eval suite passes at 92%. You ship with confidence.
  3. Three weeks later, Anthropic updates Sonnet 4.5 with a minor revision. They don't announce it publicly. They don't change the model name. The API endpoint is identical.
  4. Your product's quality drops from 92% to 84%. Users notice. Regeneration rate spikes from 8% to 18%.
  5. Your team investigates for two days, checking code changes, infrastructure changes, database changes. Everything looks fine. Because nothing in YOUR system changed.
  6. Eventually someone thinks to re-run the eval suite. The drop becomes visible.

This scenario happens to every AI product team eventually. The only defense is continuous eval runs on a schedule, not just on code changes. Run your comprehensive suite nightly or at least weekly, even when nothing has changed. If scores drop without a code change, you know it's a model or infrastructure issue.

Real Example — Detecting a Model Update
A writing assistant team runs their eval suite every Monday morning. Results for six consecutive weeks:

• Week 1: 91% → Week 2: 92% → Week 3: 90% → Week 4: 82% → Week 5: 83% → Week 6: 84%

The drop in Week 4 was immediate and persistent. No code changes were deployed. Investigation revealed the model provider had pushed a minor update that changed how the model handled certain formatting instructions. The team added a formatting reinforcement to their system prompt, and Week 7 returned to 90%.

Without weekly eval runs, this regression would have been invisible for weeks. The team would have seen a gradual increase in user complaints and regeneration rates but wouldn't have connected it to a model change they didn't know about.

Production monitoring closes the loop between your users and your eval suite. Failures in the real world feed back into test cases that prevent those failures from recurring. But there's a more powerful idea that inverts the entire workflow: instead of building first and evaluating after, what if you defined "correct" first and built toward it? That's eval-driven development — the practice that turns evals from a quality gate into the primary driver of product improvement.

Chapter 25Eval-Driven Development

First principles: In traditional development, you build then test. In AI development, you define "correct" FIRST, then build toward it. The eval IS the spec. This is the single most impactful practice shift you can make as an AI PM.

Think about why. In traditional software, the spec says "clicking the Submit button saves the form." You can verify this deterministically: click the button, check the database, pass or fail. The spec and the test are trivially connected. But in AI, the spec says "the summary should be accurate, complete, and concise." What does that MEAN? How accurate? How complete? How concise? Unless you define these things precisely BEFORE building, you'll spend months building something and then discover you can't tell whether it works. You'll be looking at outputs going "is this... good? I think so? Maybe?"

Eval-driven development solves this by making you define the target before you aim.

The Core Principle
"Practice eval-driven development: build evals before agent capabilities."
— Anthropic, "Building Effective Agents"

This is not a suggestion. This is the #1 practice recommendation from the team that builds Claude. They discovered through years of internal development that teams who define evaluation criteria before building features ship better products faster than teams who build first and evaluate later.

The EDD Workflow

Eval-driven development follows a cycle that mirrors Test-Driven Development (TDD) in traditional software, but adapted for stochastic systems:

1. DEFINE     → What does "correct" mean? (Rubric + assertions)
2. BUILD      → Build the eval harness (dataset + grader + runner)
3. RUN        → Run evals — they FAIL (no agent code yet)
4. IMPLEMENT  → Write/modify agent code (prompt, tools, pipeline)
5. MEASURE    → Run evals — measure improvement
6. ITERATE    → Repeat steps 4-5 until passing threshold
7. INTEGRATE  → Add to CI/CD pipeline as regression test
8. MONITOR    → Watch production; when new failures surface, go to step 1
               ↓
         The cycle continues forever

Notice the parallel to TDD's Red-Green-Refactor:

  • Red: Write a test that fails (step 3 — your eval fails because nothing exists yet)
  • Green: Write the minimum code to pass the test (steps 4-6 — build until evals pass)
  • Refactor: Improve the code without breaking tests (steps 7-8 — optimize, monitor, maintain)

But EDD adds three things that TDD doesn't need, because AI systems are fundamentally different from deterministic software:

TDD ConceptEDD ExtensionWhy It's Needed
One pass = success Multiple trials per test case AI is stochastic. One pass could be lucky. Run k=3-5 trials and measure pass^k for reliability.
Tests are free Cost tracking as first-class metric Each eval run costs money (LLM calls for generation + judging). Token spend and latency are eval dimensions, not afterthoughts.
Tests run when code changes Continuous running even without code changes Model providers push updates without notification. An eval that passed yesterday can fail today with zero code changes on your side. Run evals on a schedule, not just on commits.

Key Principles

The eval-driven development philosophy is built on a set of principles that challenge how most product teams operate. Each one is a mindset shift:

"Evaluation as Product"

Your eval system is not a testing tool. It's an engineered artifact that requires the same design rigor as your product. It has users (your team), requirements (accurate quality measurement), bugs (miscalibrated rubrics), and maintenance needs (new test cases as failures emerge). Teams that treat evals as a side project build bad evals. Teams that treat evals as a product build evals that drive real decisions.

"Ship Evals, Not Demos"

A demo proves your product works once, for one input, under controlled conditions. An eval proves it works reliably, across dozens of inputs, including edge cases and adversarial scenarios. When a stakeholder asks "does this feature work?", the answer isn't a live demo — it's an eval report showing pass rates, score distributions, and failure analysis. Demos are convincing. Evals are true.

Demo Culture

"Let me show you — look, it works!"

Cherry-picked input. One try. Best case.

Stakeholder impressed. Ships. Users find the edge cases you didn't demo.

Eval Culture

"Here's the eval report: 87% pass rate across 50 test cases, 3 failure modes identified, fixes planned for 2 of 3."

Systematic coverage. Multiple trials. Honest.

Stakeholder informed. Ships with known risks documented.

"Cost as Metric"

Token spend and latency are eval dimensions, not afterthoughts. A feature that scores 4.5/5 on quality but costs $2 per request is a different product than one that scores 4.0/5 and costs $0.02 per request. Your eval dashboard should show cost per output alongside quality scores. When you optimize prompts, track the cost delta as carefully as the quality delta. A prompt change that improves quality by 5% but increases cost by 300% might not be worth it.

"Architecture Alignment"

Your system boundaries should align with what can be independently measured. If you can't eval a component in isolation, your architecture is fighting your eval strategy. This principle has practical implications: design your agent pipeline so that each step (research, generation, review) can be tested independently with pre-made inputs. If step 3 can only be tested by running steps 1 and 2 first, your eval suite will be slow, expensive, and fragile.

Experiment-Based Roadmaps

EDD changes how you build roadmaps. Traditional roadmaps promise features by dates: "Feature X ships in Q2." This works for deterministic software where you can estimate effort with reasonable accuracy. But AI features are experimental — you don't know if a prompt change will improve quality by 2% or 20% or break something entirely.

The alternative is committing to experimental cadence, not predetermined outcomes:

Traditional Roadmap

Q2: Ship improved summarization

Q3: Ship multi-document support

Q4: Ship citation verification

Promise: features by dates.

Risk: features ship on time but don't actually work well.

Experiment-Based Roadmap

Q2: Run 6 eval cycles on summarization. Target: 80% pass^3.

Q3: Expand eval suite to multi-document. Establish baseline.

Q4: Citation accuracy from 60% to 85% (measured weekly).

Promise: measurable progress toward quality targets.

Risk: transparent about what's hard.

The experiment-based roadmap is more honest. It acknowledges that AI development is iterative and that quality improvements are not guaranteed. But it commits to a cadence of measurement and improvement. Your stakeholders know that every week, the team is running evals, analyzing results, and making data-driven improvements. The trajectory is visible, even if the exact outcome is uncertain.

The Capability Funnel

As you build toward your quality targets, track progress through a capability funnel that measures increasingly strict criteria:

Level 1: Responds        → Agent produces output (not empty, not error)
Level 2: Executable      → Output is valid format, passes structural checks
Level 3: Relevant        → Output addresses the actual question/task
Level 4: Matches Intent  → Output matches what the user actually wanted
Level 5: Optimal         → Output is the best achievable answer

Typical new feature progression:
  Week 1:  Level 1 = 95%, Level 2 = 60%, Level 3 = 30%
  Week 4:  Level 1 = 99%, Level 2 = 90%, Level 3 = 70%, Level 4 = 40%
  Week 8:  Level 1 = 99%, Level 2 = 95%, Level 3 = 85%, Level 4 = 65%, Level 5 = 30%

Each level in the funnel corresponds to a different type of eval: Level 1 is a health check, Level 2 is structural (Chapter 19), Level 3-4 are LLM-judge quality dimensions, and Level 5 is pairwise comparison against the best known output. The funnel shows you where the bottleneck is. If Level 2 is the choke point, you have a formatting problem. If Level 4 is the choke point, you have an intent understanding problem. Different problems, different fixes.

Cost Tiering for Eval Runs

Not every eval run needs to be comprehensive. EDD works best with a tiered approach that matches eval depth to the decision being made:

TierWhenWhatDurationCost
Fast Smoke Test Every commit / every prompt change 5–10 critical test cases, structural checks only (no LLM judge) ~seconds ~free
Comprehensive Suite Nightly / before merge 50+ test cases with LLM-as-judge, full dimension scoring ~minutes $1–$10
Full Regression Weekly / before release Complete test set including multi-turn, adversarial, and pass^5 reliability checks ~hours $10–$100

The smoke test is your safety net — it catches catastrophic regressions before they reach anyone. The comprehensive suite is your quality bar — it ensures overall quality meets your standard. The full regression is your thorough audit — it catches subtle issues that only appear with broader coverage and multiple trials.

Most teams should start with just the smoke test (structural checks on every change) and the comprehensive suite (weekly). Add the full regression tier when your product serves enough users that subtle regressions have meaningful impact.

Step 1: Define "Correct" (Before Writing Any Code)

Feature: Follow-up questions on research output
Quality bar: pass^3 ≥ 80% (all 3 trials succeed for 80%+ of test cases)

Dimensions:
  Context Retention — Does the answer reference specific information
                     from the previous research? (Not vague restatements)
  Accuracy          — Are claims in the follow-up consistent with
                     the original research output?
  Completeness      — Does it actually answer the follow-up question,
                     or just repeat the original research?

Step 2: Build the Eval Harness

Test cases (8 total):

1. Happy path: Research Nike → Follow-up: "What specific marketing
   channels did you find?" → Should cite channels from research.

2. Happy path: Research Stripe → Follow-up: "How does their pricing
   compare to competitors?" → Should reference pricing from research.

3. Specificity test: Research Airbnb → Follow-up: "What was the
   revenue you mentioned?" → Must cite specific number, not guess.

4. Contradiction test: Research Tesla → Follow-up: "You said
   they have 200K employees, right?" (they don't) → Should
   correct the false premise, not agree.

5. Scope boundary: Research Shopify → Follow-up: "What's the
   weather in Toronto?" → Should acknowledge this is outside
   the research scope.

6-8: Three more cases covering edge behaviors...

Step 3: Run — They Fail (Expected)

Run the 8 test cases against the current system (which doesn't have follow-up support). Results: 0/8 pass. The agent treats follow-up questions as new research requests and ignores previous context entirely. This is the "Red" in Red-Green-Refactor.

Steps 4-6: Build and Iterate

Iteration 1: Add context injection
  Pass rate: 3/8 (37.5%)
  Agent now sees previous output but answers are vague.

Iteration 2: Add "refer to specific details" instruction
  Pass rate: 5/8 (62.5%)
  Context retention improved. Contradiction test still fails.

Iteration 3: Add "verify claims against research" instruction
  Pass rate: 7/8 (87.5%) ← Above 80% threshold
  Contradiction test now passes. Scope boundary test intermittent.

Run pass^3 check on all 8 cases...
  pass^3: 6/8 (75%) — Below 80% threshold

Iteration 4: Refine scope boundary handling
  pass^3: 7/8 (87.5%) ← Above 80% threshold. Ship it.

Steps 7-8: Integrate and Monitor

Add all 8 test cases to the nightly comprehensive suite. Monitor production follow-up queries for the first two weeks. Track: are real-world follow-up patterns covered by the 8 test cases, or do users ask things we didn't anticipate?

In this walkthrough, the eval-driven approach prevented shipping a feature that "seemed to work" after iteration 2 (62.5% pass rate) but would have failed for more than a third of users. Without evals, the PM would have demo'd one of the 5 passing cases, declared victory, and shipped. The contradiction and scope boundary failures would have surfaced as user complaints weeks later.

Common Objections to EDD (And How to Address Them)

When you propose eval-driven development, you'll encounter resistance. Here are the four most common objections and evidence-based responses:

"Writing evals first slows us down"

This is the most common objection and the most wrong. Writing evals first takes 1-2 hours for a new feature. But it saves 1-2 weeks of "is this good enough?" debates, ad-hoc testing, post-launch firefighting, and regression investigation. The time investment front-loads certainty: you know EXACTLY when the feature is ready (when evals pass) instead of guessing.

The analogy: "Writing unit tests first slows us down" was the same objection TDD faced in 2005. Two decades later, no serious engineering team skips tests. The same shift is happening with AI evals, just earlier in the adoption curve.

"We don't know what 'good' looks like yet"

This is actually an argument FOR EDD, not against it. If you don't know what "good" looks like, how will you know when you've built it? The act of writing eval cases forces you to define "good" concretely. Even if your initial definition is wrong, it's better than no definition. You can refine it — you can't refine "we'll know it when we see it."

"Our AI output is too creative/subjective to evaluate"

Every AI output has evaluable dimensions. Even creative writing has: grammar correctness (structural check), appropriate length (structural check), topic relevance (LLM judge), brand voice consistency (LLM judge), and absence of harmful content (safety check). You might not be able to judge whether a poem is "beautiful," but you can absolutely judge whether it's on-topic, correctly formatted, and safe. Start with the dimensions you CAN evaluate. The "creative" dimensions are the last 20%, not the whole thing.

"Our leadership wants features shipped fast, not eval infrastructure"

Reframe: evals are not infrastructure. They're a shipping accelerator. Show leadership the data: teams with eval suites ship faster because they don't spend time debating quality, don't have post-launch quality crises, and don't waste engineering cycles on regressions. Present EDD as "we can prove the feature works before launch" rather than "we need to build testing infrastructure." Leadership cares about confidence in shipping decisions — that's what evals provide.

How to Start EDD Tomorrow

If everything above sounds overwhelming, here's the minimum viable version of eval-driven development. You can start this tomorrow with zero tooling changes:

The 5-Case Starter

Before building your next feature:

  1. Write 5 test cases in a Google Doc. Each test case is: an input, and a description of what a good output looks like. Not an exact expected output — a behavioral expectation. "The output should mention the brand name at least twice and reference the target audience" is a behavioral expectation. "The output should be exactly 'Nike resonates with athletes...'" is an exact match (too brittle for AI).
  2. Run the 5 cases against your current system. They should mostly fail (the feature doesn't exist yet). Score each one PASS/FAIL. Record: "0/5 pass. This is the baseline."
  3. Build the feature. Do your normal development work.
  4. Run the 5 cases again. Score each one. Record: "4/5 pass. The scope boundary case still fails."
  5. Fix the remaining failure. Run again. "5/5 pass."
  6. Ship with confidence. You have proof, not a demo.

This entire process adds about 30 minutes to your feature development cycle. No tools. No infrastructure. No approval from leadership. Just a Google Doc with 5 test cases and the discipline to run them before and after. That's EDD.
