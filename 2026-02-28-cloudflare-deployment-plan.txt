  The Request Path

  User's Browser

  What Actually Happens Step by Step

  1. User loads the app — browser hits your custom domain, Fly's edge terminates
   TLS and routes to your Fly Machine. The Machine serves the React static build
   (HTML/JS/CSS) and the browser boots up.
  2. WebSocket connects — the React app opens a WebSocket to the same Fly
  Machine. This is a persistent connection for the whole session.
  3. User sends a message — goes over WebSocket to your Fly Machine. The server
  looks up whether this user already has a sprite and session.
  4. First message (new campaign) — Fly Machine calls the Sprites SDK to create
  a new sprite. This is a REST call over public internet to Fly's Sprites API,
  which provisions a sandboxed VM. Then sprite.spawn() runs your agent-runner
  inside the sprite, passing env vars (API key) and the prompt.
  5. Inside the sprite — the agent-runner calls query() from the Claude SDK,
  which spawns a CLI subprocess. The CLI creates JSONL transcripts on the
  sprite's persistent disk. SDK output (text, tool calls, tool results) streams
  back as NDJSON.
  6. Streaming back — Sprite stdout streams over the Sprites SDK WebSocket to
  your Fly Machine, which parses the NDJSON and forwards events over your app
  WebSocket to the browser. Two hops of streaming.
  7. Campaign completes — Fly Machine stores the session ID + sprite name in
  SQLite. The sprite auto-sleeps after 30s of inactivity (compute billing stops,
   disk persists).
  8. Follow-up message — Fly Machine looks up the sprite name and session ID
  from SQLite, wakes the same sprite (100ms-2s), spawns agent-runner with the
  resume session ID. CLI reads the JSONL from persistent disk and resumes the
  conversation.
  9. Generated images — MCP saves them on the sprite's local disk. After the
  campaign, Fly Machine reads them via sprite.fs.read() (or the sprite uploads
  directly to S3/R2). Then served to the browser.

  ---
  The CDN Question

  This is where it gets important:

  Fly's edge is NOT a caching CDN. It's a routing layer — it terminates TLS and
  routes to the nearest Machine, but it does not cache your static assets at
  edge nodes worldwide. Every request for index.html or bundle.js hits your
  actual Fly Machine.

  Sprites have no CDN at all. They're internal compute sandboxes — not
  public-facing. The browser never talks to a sprite directly. Everything goes
  through your Fly Machine as a relay.

  So you have three options for static asset delivery:

  1. Do nothing — Fly Machine serves everything. Fine for low traffic, but every
   asset request hits your single Machine. Latency depends on user distance from
   your Fly region.
  2. Put Cloudflare in front — point your domain's DNS through Cloudflare. It
  caches static assets at 300+ edge locations. WebSocket connections pass
  through transparently. This is the easiest win.
  3. Separate static hosting — put the React build on something like Cloudflare
  Pages, Vercel, or Fly's Tigris (S3-compatible with built-in CDN).
  API/WebSocket still go to the Fly Machine. Adds deployment complexity but
  fully offloads static serving.

  For generated images specifically — if you go with S3/R2 +
  CloudFront/Cloudflare for storage, images get CDN delivery automatically. If
  you serve them from the Fly Machine, same problem as static assets — no edge
  caching.

  Cloudflare Sandbox SDK — The Key Facts

  What it is: A managed SDK built on Containers + Durable Objects. Full Linux
  environment per user, command execution, streaming, file management — accessed
   from Workers via a TypeScript API.

  What it can do:
  - exec() / execStream() — run arbitrary shell commands with streaming output
  - startProcess() — long-running background processes (like the Claude CLI)
  - Process group management — kills child processes too, no orphans
  - Per-user isolation — each Durable Object ID = one sandbox instance
  - Auto-sleep after inactivity (default 10 min, configurable)
  - R2 bucket mounting as local filesystem for persistence

  The persistence story is different from Sprites though:
  - Local disk is ephemeral — resets when the sandbox sleeps and wakes
  - R2 mount solves this — mount an R2 bucket as a local path, standard file
  operations work (cat, read, write), data survives across sandbox lifecycles
  - Backup/restore API also available — snapshot sandbox state to R2 before
  sleep, restore on wake
  - Trade-off: R2 mount has network latency on file operations vs Sprites'
  native persistent disk

  API Surface — What Matters for Us

  Command Execution

  Three methods, each fits a different part of the workflow:

  exec(command, options) — run and wait for result. Good for setup commands.
  exec("npm install", { cwd: "/workspace", timeout: 60000 })
  → { success, stdout, stderr, exitCode }

  execStream(command, options) — run and stream output as SSE events. This is
  the one for running the Claude SDK.
  execStream("node agent-runner.js", { env: { ANTHROPIC_API_KEY: "..." } })
  → ReadableStream of { type: "stdout"|"stderr"|"complete", data }

  startProcess(command, options) — background process with lifecycle management.
   Alternative approach — start the agent-runner as a long-running process,
  stream its logs separately.
  startProcess("node agent-runner.js", { env: {...}, processId: "campaign-123"
  })
  → Process { id, pid, status, kill(), getLogs(), waitForLog(), waitForExit() }

  All three support:
  - env — per-command environment variables (safe for API keys, not persisted to
   disk)
  - cwd — working directory
  - stdin — safe input passing (written to temp file, no shell injection)
  - timeout — max execution time

  Sandbox Lifecycle

  getSandbox(env.Sandbox, sandboxId, options)

  - sandboxId — any string. Use user-${userId} for per-user isolation.
  - sleepAfter — configurable: "30s", "5m", "1h", or seconds as number
  - keepAlive — heartbeat pings every 30s, prevents sleep (must call destroy()
  manually)
  - Lazy start — container only spins up on first exec()/writeFile()/etc, not on
   getSandbox()

  Critical detail: ALL state is lost on sleep. When the container wakes, it's a
  fresh instance from the Docker image. Files, processes, shell state —
  everything resets.

  Instance Types

  Persistence — The Three Options

  Option A: R2 Mount (simplest)
  sandbox.mountBucket("user-data", "/home/sandbox/.claude", {
    endpoint: "https://ACCOUNT.r2.cloudflarestorage.com",
    provider: "r2",
    prefix: `/users/${userId}/`
  })
  - JSONL path points at R2 via FUSE
  - CLI reads/writes directly — standard file operations, no code changes
  - Survives sleep automatically
  - Trade-off: network latency on every file op (~1-10ms per write)
  - But: CLI writes are small appends, dominant latency is Claude API (seconds)

  Option B: Backup/Restore (fastest during session)
  // Before sleep or after campaign completes:
  const backup = await sandbox.createBackup({ dir: "/home/sandbox/.claude" })
  // Store handle in D1:
  await db.run("UPDATE sessions SET backup_handle = ? WHERE id = ?",
  JSON.stringify(backup), sessionId)

  // On next wake:
  const handle = JSON.parse(await db.get("SELECT backup_handle FROM sessions
  WHERE id = ?", sessionId))
  await sandbox.restoreBackup(handle)
  - Compressed squashfs archive → R2
  - Restores as overlay mount (copy-on-write)
  - Fast local disk during active session
  - Trade-off: need orchestration logic, must backup before sleep
  - Risk: if container crashes before backup, state is lost

  Option C: R2 Mount for JSONL only, local disk for everything else
  - Mount R2 specifically at the JSONL transcript directory
  - Temp files, caches, node_modules etc stay on fast local disk
  - Best balance of persistence and performance

  The One Open Question

  WebSocket from Durable Object to browser. The current app uses a WebSocket
  connection. In the all-Cloudflare stack, the Durable Object would own the
  WebSocket to the browser and also own the sandbox. When execStream() returns
  data, the DO parses it and forwards over WebSocket. This is actually cleaner
  than the Fly architecture because the DO is both the WebSocket handler and the
   sandbox controller — no cross-machine relay.

  The architecture becomes:

  Browser ←—WebSocket—→ Durable Object ←—SDK—→ Sandbox Container
                             │
                             ├── D1 (sessions, campaigns)
                             └── R2 (JSONL, images)

  Single process (the DO) manages both the user connection and the sandbox. No
  Fly Machine in the picture at all.
